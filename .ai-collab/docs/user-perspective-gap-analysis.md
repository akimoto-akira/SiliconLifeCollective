# 用户视角缺口分析

> 生成时间: 2026-05-19 (v2 修正) | 分析视角: 非技术用户（如老师）真正坐下来用这个系统时，哪里会卡住、困惑、空转  
> 排除范围: 已识别的 6 个工程问题（NotMentionedMayReply 烧 token、ThinkOnProject 无防重入、ProjectStatus 缺 Completed、主理人意图识别缺失、群聊@输入补全、AssignedBeings 为空）

---

## 概述

本文档从**用户视角**出发，模拟一个非技术用户（如老师）首次使用"硅基生命群"系统的完整旅程，识别系统在交互体验层面的缺口。分析不聚焦代码 bug 或工程缺陷，而是聚焦于：**用户能否顺畅完成他想做的事？他知道该做什么吗？他能得到反馈吗？**

v2 修正说明：v1 中 P0-2（无法创建项目）和 P0-3（无法追踪任务进度）存在严重事实错误——ProjectView 已有创建按钮和模态框，TaskController 已完整存在。本次修正基于对 ProjectView.cs、TaskController.cs、BeingController.cs、Router.cs、ViewBase.cs 的逐行验证。

---

## P0 级：用户完全卡住，无法继续

### P0-1：首次使用零引导——初始化后用户不知道该做什么

**场景描述**：用户完成初始化表单（填写昵称、主理人名字、AI 配置、选择皮肤），系统 Redirect("/") 进入首页。此时系统里只有一个硅基主理人，没有任何项目、任务。用户面对一个显示系统指标的 Dashboard 页面。

**用户困境**：
- 初始化表单只收集了技术配置（AI 客户端类型、API Key），没有问用户"你想做什么"
- InitController 的 `HandlePost()` 完成配置后直接 `Redirect("/")`，没有任何欢迎引导
- 首页 Dashboard 显示 beingCount、activeBeings、uptime、memoryMB——对非技术用户来说是数字噪声
- 侧边栏有 💬 聊天入口（ViewBase.cs:90），但首次用户不知道聊天是核心交互方式
- 没有任何 Onboarding 流程或"快速开始"提示

**当前代码处理**：
- `InitController.cs:42`：`if (_configData.ConfigExists()) Redirect("/")` — 直接跳转，无引导
- `DashboardController.cs:59-72`：`GetStats()` 只返回技术指标
- `ViewBase.cs:88-101`：侧边栏有 chat/dashboard/beings/projects 等 11 个菜单，但没有引导用户先去哪

**建议方向**：
- 初始化完成后展示"欢迎向导"，告诉用户第一步是和主理人聊天
- Dashboard 增加面向用户的引导卡片（如"和你的主理人对话"入口按钮）
- 主理人首次苏醒时主动向用户发一条欢迎消息

### P0-2：Being 停止（Stopped）后用户可感知但无法恢复

**场景描述**：某个硅基人因连续错误 10 次进入 `Stopped` 状态。用户在 Beings 页面能看到该硅基人的 activity 显示为 "Stopped"，但不知道这意味着什么，也不知道怎么恢复。

**用户困境**：
- BeingController 的 `/api/beings/list` 返回 `activity` 字段，Being 页面能看到 "Stopped"——但只是文字展示，没有解释和操作入口
- 没有"重新启动"按钮——用户看到 Stopped 后只能干着急
- 只有当该硅基人收到新的用户消息时才可能自动恢复（`HasPendingChatWork()` 为 true 时重置错误计数），但如果错误来自内部逻辑，用户不主动给它发消息就永远停在 Stopped
- 主理人不会自动检测和恢复其他停止的硅基人

**当前代码处理**：
- `DefaultSiliconBeing.cs:172-190`：`HasPendingChatWork()` 为 true 时重置错误计数并恢复，否则设为 Stopped
- `BeingController.cs:82`：列表接口返回 `activity = b.CurrentActivity.ToString()`，页面能看到
- 没有"重启"或"恢复"的 API 和按钮

**建议方向**：
- Being 页面增加"重启"按钮，调用 ResetConsecutiveErrorCount() 并恢复
- 硅基人进入 Stopped 时通过聊天主动通知用户（主理人代为传达）
- 主理人定期检查其他硅基人状态并尝试恢复

### P0-3：任务系统入口在侧边栏缺失——用户不知道任务页面存在

**场景描述**：用户给硅基人布置了任务，想查看进度。侧边栏有 chat/dashboard/beings/usage/audit/knowledge/projects/logs/config/help/about 共 11 个菜单，但没有"任务"入口。

**用户困境**：
- TaskController 完整存在，有 `/tasks` 页面、任务列表 API、执行历史页面——但侧边栏没入口
- 项目页面有任务链接（`/project/{id}/tasks`），但用户需要先找到项目再点进去才能看到任务
- 侧边栏缺少 "tasks" 菜单项（ViewBase.cs:88-101 中没有 tasks）
- 用户不知道可以直接访问 `/tasks` 查看所有硅基人的任务

**当前代码处理**：
- `Router.cs:66-71`：TaskController 注册了完整路由
- `TaskController.cs:63-89`：`GetList()` 支持按 beingId 筛选或列出全部
- `ViewBase.cs:88-101`：侧边栏菜单没有 "tasks" 项

**建议方向**：
- 侧边栏增加"任务"菜单项
- 或者 Dashboard 增加任务统计卡片，点击进入任务页面

### P0-4：项目创建流程缺少成员分配步骤——创建后是空壳

**场景描述**：用户在项目页面点击"创建项目"按钮，填写名称、描述，选择工作流模板（可选），提交。项目创建成功。但此时项目里没有任何硅基人，也没有工作流实例。用户不知道接下来该做什么。

**用户困境**：
- ProjectView 有完整的创建模态框（名称/描述/工作流模板选择），但创建后项目是空壳
- `/api/projects/create` API 只创建项目并返回 ID，不分配硅基人、不创建工作流实例
- 没有创建成功后的引导步骤（"接下来：分配硅基人"）
- 虽然 `/api/projects/assign` API 存在，但前端没有暴露分配操作
- 用户需要回到聊天界面让主理人操作，操作路径断裂

**当前代码处理**：
- `ProjectView.cs:37`：有创建按钮 `btnCreateProject`
- `ProjectView.cs:43-67`：完整的创建模态框
- `Router.cs:122`：`/api/projects/assign` API 存在
- 但创建成功后只 `alert(loc.ProjectCreateSuccess)` + 刷新列表，无后续引导

**建议方向**：
- 创建成功后跳转到项目详情页，展示"分配硅基人"步骤
- 或创建模态框增加"选择硅基人"步骤
- 创建后主理人自动被分配为项目成员

## P1 级：体验严重受损，但用户能绕过

### P1-1：群聊中用户无法区分不同硅基人的回复

**场景描述**：用户加入了一个项目群聊，里面有主理人和 2-3 个硅基人。多个硅基人轮流回复，但流式输出（streaming）时消息来源不清晰。

**用户困境**：
- 流式传输时 `StreamChunk` 包含 `SenderName`（`WebUIProvider.cs` 中的 `StreamingBuffer.SenderName`），但前端 SSE 渲染是否正确区分不同发送者不确定
- 多个硅基人几乎同时回复时，消息交织，用户难以追踪谁说了什么
- 群聊中硅基人之间的对话对用户来说是"旁观者"视角，没有结构化的呈现

**当前代码处理**：
- `WebUIProvider.cs`：`StreamingBuffer` 有 `SenderName` 和 `SenderId` 字段
- `IIMProvider.cs`：`SendMessageAsync` 接受 `senderName` 参数
- 但 UI 渲染层的消息气泡是否按发送者分组、是否清晰标识发送者，取决于前端实现

**建议方向**：
- 群聊消息必须有清晰的发送者标识（头像/名字/颜色区分）
- 连续同一发送者的消息合并显示
- 硅基人之间的对话可折叠或标记为"内部讨论"

### P1-2：用户无法直接修改硅基人的行为/能力

**场景描述**：用户觉得某个硅基人总是回复得太长、太啰嗦，想让它更简洁。或者想让某个硅基人学会一个新技能。

**用户困境**：
- 修改硅基人行为需要修改灵魂文件（SoulContent），但用户不知道什么是灵魂文件
- CuratorTool 只有 `list_beings`、`create_being`、`get_code`、`reset` 四个操作，没有"修改灵魂"的操作
- 用户只能通过聊天间接影响硅基人行为（"请你回复简洁一点"），但这是暂时的，记忆衰减后硅基人又回到老样子
- 没有前端界面让用户查看和编辑硅基人的灵魂内容
- BeingController 有前端页面，但是否包含灵魂文件编辑功能需要确认

**当前代码处理**：
- `SiliconBeingBase.cs:107-119`：`SoulContent` 的 setter 自动保存到存储
- `CuratorTool.cs`：没有 `update_soul` 操作
- 没有面向用户的行为调整界面

**建议方向**：
- 增加用户友好的"行为偏好"设置界面（不是直接编辑灵魂文件，而是选择"简洁/详细/幽默"等风格）
- CuratorTool 增加 `update_soul` 操作
- 主理人能根据用户反馈自动调整硅基人的行为参数

---

### P1-3：权限询问弹窗打断用户，且缺乏上下文

**场景描述**：硅基人执行任务时需要访问网络或文件，触发权限询问。弹窗显示"Permission required: NetworkAccess / Resource: https://example.com / Allow code: 123456 / Deny code: 654321"。

**用户困境**：
- 权限询问弹窗是英文的、技术性的（`PermissionType` 枚举名、URL 路径），非技术用户看不懂
- 用户不知道这个请求是在什么上下文中产生的——是哪个硅基人、在做什么任务时需要这个权限
- 6 位随机码机制对网页前端来说过于复杂——网页应该直接提供"允许/拒绝"按钮，不需要输入码
- 如果用户不在网页前（比如离开电脑），请求会超时被拒，任务会失败
- 没有批量授权机制——同一个任务可能触发多次权限询问

**当前代码处理**：
- `WebUIProvider.cs:93-106`：`SendActivePermissionRequestAsync()` 发送包含 `permissionType`、`resource`、`allowCode`、`denyCode` 的消息
- `IIMProvider.cs:45`：`AskPermissionAsync` 返回 `AskPermissionResult`（Allowed + AddToCache + CacheDuration）
- 消息内容是纯技术格式，没有本地化处理

**建议方向**：
- 权限询问消息需要本地化和上下文化："小助手想访问 example.com 来查找资料，允许吗？"
- 网页前端使用按钮而非验证码
- 增加任务上下文关联——显示触发权限的具体任务
- 支持"本次任务期间全部允许"的临时授权

### P1-4：项目创建后无后续引导——用户不知道项目"活"了

**场景描述**：用户通过聊天让主理人创建了一个项目。主理人回复"项目已创建"。然后呢？

**用户困境**：
- 项目创建了但没有人被分配（AssignedBeings 为空——已识别的问题），项目只是个空壳
- 没有工作流实例被创建（已识别的问题），项目没有执行路径
- 用户不知道项目的群聊频道在哪，不知道如何查看项目进度
- 项目页面（ProjectView）只显示列表，没有"进入项目"的交互
- 用户不知道接下来该做什么——需要手动告诉主理人"给这个项目分配人"吗？

**当前代码处理**：
- `ProjectTool.cs:153-190`：`ExecuteCreate()` 只创建项目并返回 ID，不分配硅基人
- `ProjectSpace.cs:66`：`AssignedBeings` 默认为空列表
- 没有项目创建后的引导流程

**建议方向**：
- 项目创建后自动引导下一步：分配硅基人、创建工作流实例
- 在项目页面增加"进入项目群聊"的入口
- 主理人创建项目后主动提示用户可以做什么

### P1-5：记忆对用户不可见——用户不知道硅基人"记住"了什么

**场景描述**：用户和硅基人聊了很多天，想回顾一下硅基人记住了什么关于自己的信息。但找不到入口。

**用户困境**：
- MemoryController 存在（814 行），提供按时间浏览和关键词搜索功能
- 但用户不知道"记忆"是什么概念，更不知道要去 Memory 页面查看
- 记忆内容是原始的 MemoryEntry（content + timestamp + keywords），对用户不友好
- 用户无法删除或修正错误的记忆
- 用户不知道记忆会影响硅基人的行为——如果硅基人记住了错误信息，用户无法干预

**当前代码处理**：
- `Memory.cs`：`Add()`、`Query()`、`GetRecent()` 等方法完整
- `MemoryEntry.cs`：包含 Content、Keywords、Importance、State 等字段
- MemoryController 提供了 Web API，但前端是否有对应的用户友好界面未确认
- 没有用户端修正/删除记忆的功能

**建议方向**：
- 增加"硅基人记得关于你的事"的展示页面，用自然语言呈现而非原始数据
- 允许用户删除或修正特定记忆
- 在聊天界面提供"清除上下文记忆"的快捷操作

### P1-6：用户想回顾之前的对话/项目/成果，找不到

**场景描述**：用户想找上周和主理人讨论过的某个话题，或想看之前完成的项目成果。

**用户困境**：
- ChatHistoryController 存在（477 行），支持按时间搜索历史消息
- 但搜索方式是按 IncompleteDate（年/月/日），用户需要记住大致时间
- 没有全文搜索或语义搜索——用户只能按时间翻页
- 项目归档后（ProjectStatus.Archived），用户不知道去哪里找到归档的项目
- 已完成的项目成果（工作笔记、产出文件）分散在不同位置，没有统一的"成果"视图

**当前代码处理**：
- `ChatHistoryController.cs`：提供时间范围查询
- `ProjectSpace.cs`：ArchivedAt 时间戳，但没有恢复后的成果展示
- 没有全文搜索或语义搜索

**建议方向**：
- 增加聊天历史的全文搜索功能
- 增加"项目成果"页面，汇总已完成项目的产出
- 归档项目可在"历史项目"标签下找到

## P2 级：体验不佳，但不影响核心流程

### P2-1：系统响应延迟无反馈——用户不知道硅基人在"想"

**场景描述**：用户发了消息，等待硅基人回复。在 AI 处理期间（可能几秒到几十秒），聊天界面可能出现空白。

**用户困境**：
- 流式输出（streaming）时，前端有实时反馈（逐字显示）
- 但非流式输出或工具调用期间，用户可能看到长时间空白
- 用户不知道硅基人在思考、在调用工具、还是卡住了
- 队列状态（`IIMProvider.SendQueueStatusAsync`）可能存在但用户看不到

**当前代码处理**：
- `IIMProvider.cs:76`：`SendQueueStatusAsync` 接口已定义
- `WebUIProvider.cs`：是否实际调用 `SendQueueStatusAsync` 未确认
- `ContextManager.cs`：AI 请求期间没有中间状态推送

**建议方向**：
- 在 AI 处理期间显示"思考中…"或工具调用进度
- 利用已有的 QueueStatus 机制向用户展示排队位置
- 工具调用期间显示简短的进度提示（如"正在搜索…"、"正在读取文件…"）

### P2-2：创建新硅基人的流程对用户不友好

**场景描述**：用户想创建一个新的硅基人来帮忙做特定工作。他需要告诉主理人"创建一个新硅基人，名字叫小助手，灵魂是..."。

**用户困境**：
- CuratorTool 的 `create_being` 需要 `name` 和 `soul` 参数——用户需要写"灵魂文件"（即系统提示词），这不是非技术用户能做的事
- 用户理解的"创建助手"是"我需要一个会做 PPT 的助手"，而不是"我需要写一段 500 字的 system prompt"
- 没有预设的硅基人模板或角色库（如"研究助手"、"写作助手"、"数据分析助手"）
- 创建后的硅基人没有自动分配 AI 配置，可能使用全局默认配置

**当前代码处理**：
- `CuratorTool.cs:132-170`：`ExecuteCreateBeing()` 需要 name 和 soul 参数
- 没有模板系统或角色预设
- 新创建的硅基人使用全局 AI 配置

**建议方向**：
- 提供预设的硅基人角色模板（研究助手、写作助手等），用户只需选择
- 主理人根据用户描述自动生成合适的灵魂文件
- BeingController 页面增加创建硅基人的向导界面

---

### P2-3：用户无法邀请其他人一起使用

**场景描述**：老师想让同事也能使用这个系统，一起管理项目。

**用户困境**：
- 系统是单用户设计（用户 GUID 固定为 0），没有多用户概念
- 群聊的 `add_member` 操作可以添加硅基人，但不能添加其他人类用户
- 没有用户账号系统、没有邀请机制
- 需求文档 8.1.3 提到"群聊可以引入用户参与（仅网页端）"，但当前代码只支持单一用户

**当前代码处理**：
- `Config.Instance.Data.UserGuid`：固定的单一用户 GUID
- `WebUIProvider.cs`：SSE 连接基于单一用户
- 没有多用户管理代码

**建议方向**：
- 如果定位为个人工具，在 UI 上明确说明这是私人系统
- 如果未来需要协作，需要设计多用户架构
- 短期可考虑"分享项目成果"的只读链接

---

### P2-4：工作笔记对用户不可见——不知道硅基人在"写"什么

**场景描述**：硅基人在执行项目任务时会写工作笔记（WorkNoteSystem）。用户想查看这些笔记了解工作过程。

**用户困境**：
- 需求文档 12.3 节明确说"项目持有的工作笔记是公开的"
- WorkNoteSystem 有完整的 CRUD 操作
- 但用户不知道工作笔记的存在，也不知道去哪里查看
- 笔记内容可能包含重要的中间结果和决策过程
- 个人笔记默认是私密的，但用户无法区分"公开笔记"和"私密笔记"

**当前代码处理**：
- `WorkNoteSystem.cs`：完整实现，支持 SiliconBeing 和 Project 两种 OwnerType
- `WorkNoteEntry.cs`：有 Visibility 属性（Private/Public）
- ProjectWorkNoteTool 存在于工具列表中
- 但 Web 端没有笔记浏览界面

**建议方向**：
- 项目页面增加"工作笔记"标签页
- 聊天中可引用/展示项目笔记内容
- 区分"硅基人私人笔记"和"项目公开笔记"的展示方式

### P2-5：定时器/定时任务的设置对用户不直观

**场景描述**：用户想让硅基人每天早上提醒自己今天的课程安排。用户说"每天早上 8 点提醒我课程安排"。

**用户困境**：
- 定时器系统（TimerSystem）基于历法系统，支持复杂时间规则
- 但定时器只能通过聊天让 AI 创建——用户无法直接查看和管理已有的定时器
- TimerController 存在（476 行），提供 Web 界面
- 但用户可能不知道"定时器"对应的概念，他只知道自己说过"每天提醒我"
- 如果定时器触发失败或被遗忘，用户不知道
- 修改或取消定时器需要再次通过聊天

**当前代码处理**：
- `TimerSystem.cs`：完整的定时器管理
- `TimerTool.cs`：AI 可调用工具
- `TimerController.cs`：Web 界面存在

**建议方向**：
- 聊天中设置定时器后，显示确认信息和下次触发时间
- 定时器列表页面增加"创建定时器"的表单入口
- 定时器触发后向用户发送通知

### P2-6：AI 配置切换/错误时用户无感知

**场景描述**：AI 服务暂时不可用（如 API Key 过期、网络中断），硅基人的请求失败。

**用户困境**：
- `ContextManager.cs:715-722`：连接错误时自动回退到全局配置（fallback），但用户不知道
- `DefaultSiliconBeing.cs:493-523`：`CheckAndRebuildAIClient()` 检测配置变更并重建客户端，但无用户通知
- 用户只看到硅基人回复变慢或质量下降，不知道原因
- 如果 fallback 配置也不可用，AI 请求会失败，但错误信息是英文的（"AI request failed: ..."）
- `ThinkOnChat()` 失败时返回 `[Error] AI request failed: ...`，对用户不够友好

**当前代码处理**：
- `ContextManager.cs:903-906`：`DeliverOutput($"[Error] AI request failed: {errorMsg}")`
- `DefaultSiliconBeing.cs:362-366`：错误信息记录到 Memory 和日志
- 没有面向用户的错误说明

**建议方向**：
- AI 配置异常时通知用户（"当前 AI 服务不可用，正在使用备用服务"）
- 错误信息本地化和人性化："抱歉，我现在无法处理消息，请稍后再试"
- Web 界面增加 AI 服务状态指示器

### P2-7：项目工作流进展对用户不透明

**场景描述**：用户创建了一个带工作流模板的项目。工作流在后台推进状态转换，但用户看不到进展。

**用户困境**：
- `WorkflowEngine.cs`：`TickAsync()` 每 60 秒检查活跃实例并尝试转换
- `WorkflowInstance` 有 CurrentState、Status、BusinessKey 等信息
- 但用户看不到工作流的当前状态、下一步是什么、还需要多久
- 工作流卡住时（没有满足条件的转换），用户不知道
- 没有前端工作流可视化

**当前代码处理**：
- `WorkflowEngine.cs:168-182`：Tick 驱动状态转换
- `WorkflowEngine.cs:197-200`：按优先级查找可执行的转换
- 没有 Web 端的工作流展示

**建议方向**：
- 项目详情页增加工作流状态可视化
- 工作流状态变更时通知用户
- 卡住时显示"需要手动干预"的提示

### P2-8：硅基人之间的协作过程对用户是个黑箱

**场景描述**：主理人把任务分发给多个硅基人协作完成。硅基人之间在群聊中讨论、在工作笔记中记录。用户只是旁观者。

**用户困境**：
- 硅基人之间的通信通过群聊频道和广播频道进行
- 用户不知道硅基人之间在讨论什么、进度如何
- 如果协作出现问题（如两个硅基人做了重复的工作），用户不知道
- 广播消息只在硅基人之间流转（`DefaultSiliconBeing.cs:273-288`），用户看不到
- 用户感觉自己被排除在"团队"之外

**当前代码处理**：
- `DefaultSiliconBeing.cs:273-288`：广播处理只写入 Memory 并标记已读，不通知用户
- 项目群聊消息用户可以看到（如果是成员），但硅基人之间的私聊看不到
- 没有协作过程可视化

**建议方向**：
- 项目群聊中用户始终是成员，能看到硅基人之间的讨论
- 关键节点（任务分配、完成、问题）主动通知用户
- 增加"协作动态"时间线视图

## 核心主题归纳

以上 18 个缺口可以归纳为 **5 个系统性问题**：

1. **可发现性缺失**（P0-1, P0-3, P1-4, P2-5）：系统的能力隐藏在聊天背后，用户不知道能做什么、怎么做。已有页面如任务系统被"埋"了，侧边栏没有入口。需要把"通过聊天操作"的隐式交互，变为"聊天+界面"的双通道交互。

2. **反馈真空**（P0-2, P2-1, P2-6, P2-7）：用户发出指令后，缺乏中间状态和结果反馈。Being 停止了没有主动通知，AI 异常了用户不知道，工作流推进了看不到。系统内部有完整的状态机，但缺少向用户的推送机制。

3. **技术概念暴露**（P1-3, P2-2, P2-6）：权限验证码、灵魂文件、AI 配置错误等技术细节直接暴露给非技术用户。需要用用户能理解的语言重新包装。

4. **数据孤岛**（P1-5, P1-6, P2-4, P2-8）：记忆、工作笔记、协作过程、项目成果等有价值的信息分散在系统中，用户无法统一访问和搜索。

5. **流程断裂**（P0-4, P1-4, P1-2）：用户执行了一个操作（创建项目、布置任务），但缺少下一步引导。项目创建后没人、任务布置后看不到进度、硅基人行为偏离后无法调整——每一步都像走到了路的尽头。

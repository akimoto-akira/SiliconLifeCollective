# 安全設計

> **版本：v0.2.0-alpha**

[English](../en/security.md) | [中文](../zh-CN/security.md) | **繁體中文** | [Español](../es-ES/security.md) | [日本語](../ja-JP/security.md) | [한국어](../ko-KR/security.md) | [Čeština](../cs-CZ/security.md)

## 概述

Silicon Life Collective 的安全性建立在**分層防禦**模型之上。核心原則：**所有 I/O 操作必須透過執行器**，執行器在執行前強制執行權限檢查。

```
工具呼叫 → 執行器 → 權限管理器 → 頻率快取 → 回呼 → (IsCurator: 詢問使用者 | Non-curator: 全域ACL)
```

---

## 權限模型

### 權限類型

| 類型 | 描述 |
|------|------|
| `NetworkAccess` | 出站 HTTP/HTTPS 請求 |
| `CommandLine` | Shell 命令執行 |
| `FileAccess` | 檔案和目錄操作 |
| `Function` | 敏感函式呼叫 |
| `DataAccess` | 存取系統或使用者資料 |

### 權限結果

每次權限檢查回傳三種結果之一：

| 結果 | 行為 |
|--------|----------|
| **Allowed（允許）** | 操作立即進行 |
| **Denied（拒絕）** | 操作被阻止，記錄稽核日誌 |
| **AskUser（詢問使用者）** | 操作暫停，需要使用者確認 |

### 特殊角色：矽基主理人

矽基主理人擁有最高權限級別（`IsCurator = true`）。當權限鏈到達分支判斷時，主理人的操作會透過 `IPermissionAskHandler` 詢問使用者確認，而非直接短路為允許。非主理人則查詢全域 ACL。

### 私有權限管理器

每個矽基生命體都有自己的**私有 PermissionManager** 實例。權限狀態不在生命體之間共享。

---

## 權限驗證流程

查詢優先順序為：**1. 頻率快取 → 2. 回呼函式 → 3. 分支判斷（IsCurator/GlobalACL）**

```
┌─────────────┐
│ 工具呼叫     │
└──────┬──────┘
       │
       ▼
┌─────────────┐     ┌─────────────────────┐
│  執行器      │────▶│ 私有權限            │
│（磁碟/網絡/  │     │ 管理器（每個生命體）  │
│  命令列...） │     └────────┬────────────┘
└─────────────┘            │
                           ▼
                  ┌─────────────────┐
                  │ 1. 頻率快取      │──匹配──▶ 允許 / 拒絕
                  │（高拒絕優先於    │
                  │   高允許）       │
                  └────────┬────────┘
                           │ 未匹配
                           ▼
                  ┌─────────────────┐
                  │ 2. 權限         │
                  │  回呼函式        │──▶ 允許 / 拒絕 / 詢問使用者
                  └────────┬────────┘
                           │ 詢問使用者
                           ▼
                  ┌─────────────────┐
                  │ 3. IsCurator?   │
                  └────────┬────────┘
                           │
                 ┌─────────┴─────────┐
                 │                   │
                 ▼ 是                ▼ 否
          ┌─────────────┐    ┌─────────────┐
          │ 詢問使用者   │    │ 全域 ACL     │
          │（AskHandler）│    │ 查詢規則     │
          └─────────────┘    └─────────────┘
```

**關鍵點**：執行器只看到布林值（允許/拒絕）。權限管理器內部處理三元決策（允許/拒絕/詢問使用者），並在回傳給執行器之前解決詢問使用者。

## 執行器（安全邊界）

執行器是 I/O 操作的**唯一**路徑。它們強制執行：

### 獨立排程執行緒

每個執行器擁有**獨立的排程執行緒**：

- 執行器之間的執行緒隔離 —— 一個執行器的執行緒阻塞不影響其他執行器。
- 每個執行器可以設定獨立的資源限制（CPU、記憶體等）。
- 執行器執行緒的執行緒池管理。

### 請求佇列

每個執行器維護一個請求佇列：

- 請求按類型路由到相應的執行器。
- 支援優先順序排隊。
- 每個請求的逾時控制。

### 權限驗證的執行緒鎖定

當工具發起資源存取時：

1. 執行器接收請求並**鎖定其執行緒**。
2. 執行器查詢生命體的私有權限管理器。
3. 如果回呼回傳詢問使用者，執行器執行緒**保持鎖定**等待使用者回應。
4. 生命體只看到最終結果（成功或拒絕） —— 它永遠不會看到中間的「待處理」或「等待」狀態。
5. 只有矽基主理人會觸發真正的使用者提示。普通生命體同步查詢全域 ACL 而不阻塞。
6. 逾時時，請求被視為拒絕，執行緒鎖被釋放。

### 執行器類型

| 執行器 | 範圍 | 預設逾時 |
|----------|-------|-----------------|
| `DiskExecutor` | 檔案讀/寫、目錄操作 | 30 秒 |
| `NetworkExecutor` | HTTP 請求、WebSocket 連線 | 60 秒 |
| `CommandLineExecutor` | Shell 命令執行 | 120 秒 |

> **注意**：`DynamicCompilationExecutor`（位於 `SiliconLife.Core.Compilation` 命名空間）負責 Roslyn 記憶體編譯，不屬於 I/O 執行器範疇，但同樣受權限系統約束。

### 異常隔離與容錯

- 一個執行器的異常不影響其他執行器。
- 執行緒崩潰時自動重啟。
- 熔斷器：連續失敗後暫時停止執行器以防止級聯失敗。

## 全域 ACL（存取控制列表）

共享規則表持久化到儲存，僅由矽基主理人管理：

```json
{
  "rules": [
    { "prefix": "network:api.github.com", "result": "Allowed" },
    { "prefix": "file:C:\\Windows", "result": "Denied" },
    { "prefix": "cli:rm -rf", "result": "Denied" }
  ]
}
```

- 規則按順序評估；第一次匹配獲勝。
- 只有矽基主理人可以修改全域 ACL（透過其專用工具）。
- 變更立即生效。
- 全域 ACL **不在**上述每個查詢的優先順序鏈中 —— 它在內部由回呼函式引用。

## 使用者頻率快取

為減少重複的權限提示，系統維護兩個**每個生命體、僅記憶體**的快取：

| 快取 | 用途 |
|-------|---------|
| **HighAllow（高允許）** | 使用者頻繁允許的資源 |
| **HighDeny（高拒絕）** | 使用者頻繁拒絕的資源 |

### 運作方式

- **使用者選擇，非自動偵測**：當觸發詢問使用者時，使用者選擇是否將資源新增到快取。
- **前綴匹配**：支援資源路徑前綴匹配（例如 `network:api.example.com/*`）。
- **優先順序**：高拒絕的優先順序高於高允許。
- **僅記憶體**：快取不持久化。重啟時遺失。
- **可設定過期**：使用者可以設定快取條目的有效期限。

### 快取更新流程

1. 權限回呼回傳 `AskUser`。
2. 權限系統向卡片系統（Web UI 或即時通訊）發送查詢。
3. 使用者做出決策（允許/拒絕）並**選擇是否快取**。
4. 卡片系統回傳決策 + 快取標誌。
5. 權限系統更新相應的快取列表。
6. 未來匹配快取前綴的請求立即解決。

## 使用者詢問機制

當權限檢查回傳 `AskUser` 時：

### Web UI：互動式卡片

Web 前端立即顯示**互動式卡片**，顯示：
- 資源類型和路徑
- 操作描述
- 允許 / 拒絕按鈕
- 可選的「始終允許」/「始終拒絕」核取方塊（新增到頻率快取）

### 即時通訊（無卡片支援）：隨機碼

對於不支援互動式卡片的訊息傳遞平台：

1. 系統生成兩個隨機 6 位代碼：**允許代碼**和**拒絕代碼**。
2. 發送包含資源資訊和兩個代碼的訊息。
3. 使用者必須回覆準確的允許代碼才能授權。任何其他回覆被視為拒絕。
4. 代碼是單次使用的，以防止重放攻擊。

### 逾時

- 為所有詢問使用者請求設定逾時。
- 逾時時，請求被視為**拒絕**，執行器執行緒鎖被釋放。

## 動態編譯安全

自我進化（類別重寫）引入了獨特的安全風險。系統使用**分層策略**緩解它們：

### 第 1 層：編譯時引用控制（主要防禦）

- 編譯器只獲得**允許的組件引用列表**。
- **允許**：`System.Runtime`、`System.Private.CoreLib`、專案組件（ITool 介面等）
- **阻止**：`System.IO`、`System.Reflection`、`System.Runtime.InteropServices` 等
- 如果程式碼引用了被阻止的組件，**編譯器本身拒絕**程式碼。
- 這比執行時掃描更可靠 —— 危險操作在類型級別是不可能的。

### 第 2 層：執行時靜態分析（次要防禦）

- 即使成功編譯後，程式碼也要進行靜態模式掃描。
- 偵測危險操作模式（直接 I/O、系統呼叫等）。
- 如果發現危險程式碼，載入被拒絕，系統回退到預設功能。

### 繼承約束

所有自訂矽基生命體類別**必須**繼承 `SiliconBeingBase`。編譯器在類型級別強制執行此約束。

### 加密儲存

編譯的程式碼在磁碟上以 AES-256 加密儲存：

- **金鑰派生**：從生命體的 GUID（大寫）使用 PBKDF2。
- **解密失敗**：回退到預設實作。
- **執行時重新編譯**：新程式碼先在記憶體中編譯；只有在成功編譯和實例替換後才持久化。

### 原子替換

替換過程是原子的：

1. 在記憶體中編譯新程式碼 → 取得 `Type`。
2. 從 `Type` 建立新實例。
3. 從舊實例遷移狀態到新實例。
4. 交換引用。
5. 持久化加密程式碼。

如果任何步驟失敗，舊實例保持活動。

## 權限回呼函式

### 設計

每個 PermissionManager 持有**回呼函式變數**：

- **預設**：指向內建預設權限函式。
- **動態編譯後**：被生命體的自訂權限函式覆寫。
- **二擇一**：任何時候只有一個回呼處於活動狀態。
- **編譯失敗**：不影響目前回呼 —— 預設或上次成功的自訂函式保持有效。

### 回呼簽名

```
PermissionResult Callback(PermissionType type, string resourcePath, Guid callerId)
```

回傳 `Allowed`、`Denied` 或 `AskUser`。

## 稽核日誌

所有權限決策都被記錄：

```
[2026-04-01 15:30:25] ALLOWED  | Being:AssistantA | Type:NetworkAccess | Resource:api.github.com | Source:HighAllowCache
[2026-04-01 15:30:26] DENIED   | Being:AssistantB | Type:FileAccess    | Resource:C:\Windows\System32 | Source:HighDenyCache
[2026-04-01 15:30:27] ASK_USER | Being:Curator    | Type:CommandLine   | Resource:del /f /q *.log | Source:Callback
[2026-04-01 15:30:28] ALLOWED  | Being:Curator    | Type:CommandLine   | Resource:del /f /q *.log | Source:UserDecision
```

日誌持久化到儲存，可透過 Web UI（日誌控制器）檢視。

## Token 使用稽核

`TokenUsageAuditManager` 提供與安全性相關的 AI Token 消耗追蹤：

- **每次請求記錄** —— 每次 AI 呼叫記錄生命體 ID、模型、提示詞 Token、補全 Token 和時間戳。
- **異常偵測** —— 異常的 Token 消耗模式可能表明提示詞注入或資源濫用。
- **僅主理人存取** —— `TokenAuditTool`（標記為 `[SiliconManagerOnly]`）允許主理人查詢和彙總 Token 使用。
- ** Web 儀表板** —— `UsageController` 提供基於瀏覽器的儀表板，帶趨勢圖和資料匯出。
- **持久化儲存** —— 記錄透過 `ITimeStorage` 儲存，用於時間序列查詢和長期分析。

## 外掛程式安全

外掛程式系統引入了第三方程式碼執行的安全風險，透過以下機制緩解：

### 安全沙箱

`PluginLoader` 在載入外掛程式時執行嚴格的安全掃描：

1. **禁止命名空間檢查** — 外掛程式不能引用以下命名空間：
   - `System.IO` — 檔案系統存取
   - `System.Net.Http` — HTTP 請求
   - `System.Net.WebSockets` — WebSocket 連線
   - `System.Net.Sockets` — 原始通訊端
   - `Microsoft.CodeAnalysis` — 編譯器 API

2. **可信組件白名單** — 以下組件的引用被允許：
   - `Google.Protobuf`、`Newtonsoft.Json`、`MessagePack`
   - `Serilog`、`Microsoft.Extensions.Logging.Abstractions`
   - `Dapper`

3. **禁止類型檢查** — 掃描外掛程式中引用的危險類型

4. **禁止成員檢查** — 掃描外掛程式中呼叫的危險方法

### 隔離載入

- 使用自訂 `AssemblyLoadContext` 隔離載入每個外掛程式
- 外掛程式之間的類型和組件不會互相干擾
- 外掛程式卸載時可以釋放相關資源

### 工具權限約束

- 外掛程式透過 `ITool` 介面註冊的工具受相同的權限系統約束
- 外掛程式工具不能繞過 5 級權限鏈
- 外掛程式工具受 `[SiliconManagerOnly]` 標記約束

## Участие в двухверсионном проекте

Этот проект имеет две версии реализации, вы можете выбрать направление участия в зависимости от интересов:

### SiliconLife.Default (версия по умолчанию)
- **Технологический стек**: консольное приложение .NET 9
- **Направление участия**: разработка основных функций, реализация инструментов, локализация, документация
- **Подходит для**: всех разработчиков

### SiliconLife.Fast (высокопроизводительная версия)
- **Технологический стек**: кроссплатформенное настольное приложение .NET 9 (Avalonia UI)
- **Направление участия**: оптимизация производительности, хранение SpeedyPack, системный трей, неблокирующая параллельность
- **Подходит для**: разработчиков с опытом настольной разработки, интересующихся оптимизацией производительности

> **Важное замечание**: обе версии совместно используют проекты SiliconLife.Core и SiliconLife.Common, улучшения основных интерфейсов затронут обе версии одновременно.

## Кодекс поведения

Этот проект следует лицензии Apache 2.0. Будьте уважительны и профессиональны во всех взаимодействиях.

## Быстрый старт

### 1. Форкните репозиторий

Нажмите кнопку «Fork» на GitHub, чтобы создать свою копию.

### 2. Клонируйте ваш форк

```bash
git clone https://github.com/akimoto-akira/SiliconLifeCollective.git
cd SiliconLifeCollective
```

### 3. Настройте среду разработки

```bash
# Установите .NET 9 SDK
# https://dotnet.microsoft.com/download/dotnet/9.0

# Восстановите зависимости
dotnet restore

# Соберите проект
dotnet build

# Запустите тесты
dotnet test
```

### 4. Создайте ветку функции

```bash
git checkout -b feature/your-feature-name
```

### 5. Выберите проект для разработки

В зависимости от типа вашего участия выберите подходящий проект:

- **Основные интерфейсы/абстрактные классы** → изменяйте `SiliconLife.Core`
- **Общие реализации** → изменяйте `SiliconLife.Common`
- **Специфичное для версии Default** → изменяйте `SiliconLife.Default`
- **Специфичное для версии Fast** → изменяйте `SiliconLife.Fast`
- **Движок хранения** → изменяйте `SiliconLife.Speedy`
- **Инструмент управления хранилищем** → изменяйте `SiliconLife.Speedy.Manager`
- **Разработка плагинов** → изменяйте `SiliconLife.Core/Plugins`
- **Многоязычная документация** → изменяйте каталог `docs/`

## Рабочий процесс разработки

### Стиль кода

- Следуйте соглашениям C#
- Имена классов используйте PascalCase
- Параметры методов используйте camelCase
- Приватные поля используйте `_camelCase`
- Все публичные API должны иметь XML-документацию

### Сообщения коммитов

Следуйте формату **конвенциональных коммитов**:

```
<type>(<scope>): <description>
```

**Типы**:
- `feat`: новая функция
- `fix`: исправление бага
- `docs`: изменение документации
- `style`: форматирование кода
- `refactor`: рефакторинг кода
- `test`: изменение тестов
- `chore`: изменение сборки/инструментов

**Примеры**:
```bash
feat(localization): add Korean language support
fix(permission): fix null pointer in callback
docs: update contributing guide
refactor(web): simplify controller structure
```

### Внесение изменений

1. **Напишите код**
   - Следуйте существующим паттернам
   - Добавьте тесты для новых функций
   - Обновите документацию

2. **Протестируйте ваши изменения**
   ```bash
   # Запустите все тесты
   dotnet test
   
   # Соберите в режиме Release
   dotnet build --configuration Release
   ```

3. **Отформатируйте код**
   ```bash
   dotnet format
   ```

4. **Зафиксируйте изменения**
   ```bash
   git add .
   git commit -m "feat(scope): description"
   ```

5. **Отправьте в ваш форк**
   ```bash
   git push origin feature/your-feature-name
   ```

6. **Создайте Pull Request**
   - Перейдите в исходный репозиторий
   - Нажмите «Compare & pull request»
   - Заполните шаблон PR
   - Отправьте

## Руководство по Pull Request

### Заголовок PR

Используйте тот же формат, что и для сообщений коммитов:
```
feat(localization): add Korean language support
```

### Описание PR

Включите:

1. **Что** — что делает этот PR?
2. **Почему** — зачем нужно это изменение?
3. **Как** — как вы это реализовали?
4. **Тестирование** — как вы это тестировали?

### Пример описания PR

```markdown
## Что
Добавлена корейская локализация для всех UI-компонентов и документации.

## Почему
Расширение доступности проекта для корейскоязычных пользователей.

## Как
- Создан файл локализации KoKR.cs
- Добавлено 500+ ключей перевода
- Обновлены все представления для использования локализации
- Создана корейская документация в docs/ko-KR/

## Тестирование
- Проверено корректное отображение корейского языка во всех элементах UI
- Протестирована функция переключения языка
- Переводы проверены носителями языка
```

## Типы участия

### 1. Исправление багов

**Процесс**:
1. Проверьте существующие Issues
2. Если Issue не существует, создайте его
3. Исправьте баг
4. Добавьте тест-кейс
5. Отправьте PR

**Требования**:
- Чёткое описание бага
- Шаги воспроизведения
- Тест для предотвращения регрессии

### 2. Новые функции

**Процесс**:
1. Обсудите функцию в Issues/Discussions
2. Получите одобрение мейнтейнера
3. Реализуйте функцию
4. Добавьте полные тесты
5. Обновите документацию
6. Отправьте PR

**Требования**:
- Предложение функции одобрено
- Полное покрытие тестами
- Документация обновлена
- Обратная совместимость

### 3. Документация

**Процесс**:
1. Определите пробелы в документации
2. Напишите/обновите документацию
3. Отправьте PR

**Требования**:
- Ясность и лаконичность
- Включите примеры
- Поддержка нескольких языков (если применимо)

### 4. Рефакторинг кода

**Процесс**:
1. Предложите рефакторинг в Issue
2. Получите одобрение
3. Проведите рефакторинг
4. Убедитесь, что все тесты проходят
5. Отправьте PR

**Требования**:
- Без изменения функциональности
- Все тесты проходят
- Улучшение качества кода
- Чёткое объяснение

## Руководство по тестированию

### Модульные тесты

```csharp
[TestMethod]
public void MyFeature_ShouldWork_AsExpected()
{
    // Подготовка
    var service = new MyService();
    
    // Выполнение
    var result = service.DoSomething();
    
    // Проверка
    Assert.IsTrue(result.Success);
}
```

### Интеграционные тесты

Тестирование полного рабочего процесса:
- Взаимодействие с AI
- Выполнение инструментов
- Проверка разрешений
- Операции хранения

### Ручное тестирование

Для изменений UI:
- Тестируйте в нескольких браузерах
- Проверяйте адаптивный дизайн
- Проверяйте доступность

## Руководство по документации

### Комментарии в коде

- Используйте XML-комментарии для всех публичных API
- Используйте встроенные комментарии для сложной логики
- Комментарии в коде пишите на английском

### Файлы документации

- Размещайте в `docs/{language}/`
- Обновляйте все языковые версии
- Следуйте существующей структуре

### Многоязычная документация

При добавлении документации:
1. Сначала создайте английскую версию
2. Переведите на другие языки
3. Поддерживайте синхронизацию содержимого

## Процесс рецензирования

### Что проверяют мейнтейнеры

1. **Качество кода**
   - Следование соглашениям
   - Ясность и читаемость
   - Документированность

2. **Тестирование**
   - Достаточное покрытие
   - Все тесты проходят
   - Покрытие граничных случаев

3. **Документация**
   - Обновлена
   - Ясные объяснения
   - Многоязычность

4. **Совместимость**
   - Обратная совместимость
   - Отсутствие ломающих изменений (если не согласовано)
   - Следование семантическому версионированию

### Сроки рецензирования

- Первичная рецензия: 1-3 дня
- Интеграция обратной связи: по необходимости
- Слияние: после одобрения

## Часто задаваемые вопросы

### PR отклонён

**Причины**:
- Несоблюдение руководящих принципов
- Недостаточное тестирование
- Несогласованные ломающие изменения
- Низкое качество кода

**Решение**:
- Устраните замечания
- Обновите PR
- Повторно отправьте

### Конфликты слияния

**Решение**:
```bash
# Обновите вашу ветку
git fetch origin
git rebase origin/master

# Разрешите конфликты
# Отредактируйте конфликтующие файлы
git add .
git rebase --continue

# Принудительная отправка
git push --force-with-lease
```

# Проектирование безопасности

> **Версия: v0.2.0-alpha**

[English](../en/security.md) | [Deutsch](../de-DE/security.md) | [中文](../zh-CN/security.md) | [繁體中文](../zh-HK/security.md) | [Español](../es-ES/security.md) | [日本語](../ja-JP/security.md) | [한국어](../ko-KR/security.md) | [Čeština](../cs-CZ/security.md) | **Русский**

## Обзор

Безопасность Silicon Life Collective основана на модели **многоуровневой защиты**. Основной принцип: **все операции I/O должны проходить через Исполнители**, которые принудительно выполняют проверку разрешений перед выполнением.

```
Вызов Инструмента → Исполнитель → Менеджер Разрешений → Кэш Частоты → Обратный вызов → (IsCurator: запрос пользователю | Non-curator: Глобальный ACL)
```

---

## Модель разрешений

### Типы разрешений

| Тип | Описание |
|------|-------------|
| `NetworkAccess` | Исходящие HTTP/HTTPS-запросы |
| `CommandLine` | Выполнение Shell-команд |
| `FileAccess` | Файловые и каталоговые операции |
| `Function` | Вызов конфиденциальных функций |
| `DataAccess` | Доступ к системным или пользовательским данным |

### Результаты разрешений

Каждая проверка разрешений возвращает один из трёх результатов:

| Результат | Поведение |
|--------|----------|
| **Allowed (Разрешено)** | Операция выполняется немедленно |
| **Denied (Отказано)** | Операция блокируется, записывается в аудитный журнал |
| **AskUser (Запрос пользователю)** | Операция приостанавливается, требуется подтверждение пользователя |

| Специальная роль: Кремниевый Куратор

Кремниевый Куратор обладает высшим уровнем полномочий (`IsCurator = true`). Когда цепочка разрешений достигает ветвления, операции Куратора запрашивают подтверждение пользователя через `IPermissionAskHandler`, а не автоматически разрешаются. Не-Кураторы проверяются через Глобальный ACL.

### Приватный Менеджер Разрешений

Каждое Кремниевое Существо имеет свой собственный **приватный экземпляр PermissionManager**. Состояние разрешений не разделяется между существами.

---

## Процесс проверки разрешений

Приоритет запроса: **1. Кэш частоты → 2. Функция обратного вызова → 3. Ветвление (IsCurator/GlobalACL)**

```
┌─────────────┐
│ Вызов       │
│ инструмента │
└──────┬──────┘
       │
       ▼
┌─────────────┐     ┌─────────────────────┐
│  Исполнитель│────▶│ Приватный           │
│(диск/сеть/  │     │ Менеджер            │
│командная    │     │ Разрешений          │
│строка...)   │     │ (для каждого        │
└─────────────┘     │  существа)          │
                    └────────┬────────────┘
                             │
                             ▼
                  ┌─────────────────┐
                  │ 1. Кэш частоты  │──совпадение──▶ Разрешено / Отказано
                  │(HighDeny        │
                  │ приоритет над   │
                  │ HighAllow)      │
                  └────────┬────────┘
                           │ Нет совпадения
                           ▼
                  ┌─────────────────┐
                  │ 2. Функция      │
                  │ обратного вызова│──▶ Разрешено / Отказано / Запрос пользователю
                  │ разрешений      │
                  └────────┬────────┘
                           │ Запрос пользователю
                           ▼
                  ┌─────────────────┐
                  │ 3. IsCurator?   │
                  └────────┬────────┘
                           │
                 ┌─────────┴─────────┐
                 │                   │
                 ▼ Да                ▼ Нет
          ┌─────────────┐    ┌─────────────┐
          │ Запрос       │    │ Глобальный  │
          │ пользователю │    │ ACL         │
          │(AskHandler)  │    │ Запрос      │
          └─────────────┘    │ правил      │
                             └─────────────┘
```

**Ключевой момент**: Исполнитель видит только логическое значение (разрешено/отказано). Менеджер Разрешений внутренне обрабатывает трёхзначное решение (разрешено/отказано/запрос пользователю) и разрешает запрос пользователю перед возвратом результата Исполнителю.

## Исполнители (граница безопасности)

Исполнители — **единственный** путь для операций I/O. Они обеспечивают:

### Отдельный поток планирования

Каждый Исполнитель имеет **отдельный поток планирования**:

- Изоляция потоков между Исполнителями — блокировка потока одного Исполнителя не влияет на другие Исполнители.
- Каждый Исполнитель может устанавливать независимые ограничения ресурсов (CPU, память и др.).
- Управление пулом потоков Исполнителя.

### Очередь запросов

Каждый Исполнитель поддерживает очередь запросов:

- Запросы маршрутизируются к соответствующему Исполнителю по типу.
- Поддержка приоритетной очереди.
- Контроль тайм-аута для каждого запроса.

### Блокировка потока при проверке разрешений

Когда инструмент инициирует доступ к ресурсу:

1. Исполнитель получает запрос и **блокирует свой поток**.
2. Исполнитель запрашивает приватный Менеджер Разрешений существа.
3. Если обратный вызов возвращает «Запрос пользователю», поток Исполнителя **остаётся заблокированным** в ожидании ответа пользователя.
4. Существо видит только окончательный результат (успех или отказ) — оно никогда не видит промежуточное состояние «ожидание» или «в процессе».
5. Только Кремниевый Куратор инициирует реальный запрос пользователю. Обычные существа синхронно запрашивают Глобальный ACL без блокировки.
6. При тайм-ауте запрос считается отклонённым, блокировка потока снимается.

### Типы Исполнителей

| Исполнитель | Область действия | Тайм-аут по умолчанию |
|----------|-------|-----------------|
| `DiskExecutor` | Чтение/запись файлов, операции с каталогами | 30 секунд |
| `NetworkExecutor` | HTTP-запросы, WebSocket-соединения | 60 секунд |
| `CommandLineExecutor` | Выполнение Shell-команд | 120 секунд |

> **Примечание**: `DynamicCompilationExecutor` (в пространстве имён `SiliconLife.Core.Compilation`) отвечает за компиляцию в памяти Roslyn и не относится к категории I/O Исполнителей, но также подчиняется системе разрешений.

### Изоляция исключений и отказоустойчивость

- Исключение одного Исполнителя не влияет на другие Исполнители.
- Автоматический перезапуск при сбое потока.
- Автоматический Выключатель: временная остановка Исполнителя после последовательных сбоев для предотвращения каскадных ошибок.

## Глобальный ACL (Список Контроля Доступа)

Общая таблица правил, персистентная в хранилище, управляемая только Кремниевым Куратором:

```json
{
  "rules": [
    { "prefix": "network:api.github.com", "result": "Allowed" },
    { "prefix": "file:C:\\Windows", "result": "Denied" },
    { "prefix": "cli:rm -rf", "result": "Denied" }
  ]
}
```

- Правила оцениваются по порядку; первое совпадение побеждает.
- Только Кремниевый Куратор может изменять Глобальный ACL (через свой специализированный инструмент).
- Изменения вступают в силу немедленно.
- Глобальный ACL **не входит** в вышеуказанную приоритетную цепочку каждого запроса — он внутренне ссылается на функцию обратного вызова.

## Кэш частоты пользователя

Для уменьшения повторяющихся запросов разрешений система поддерживает два **для каждого существа, только в памяти** кэша:

| Кэш | Назначение |
|-------|---------|
| **HighAllow (Высокое разрешение)** | Ресурсы, часто разрешаемые пользователем |
| **HighDeny (Высокий отказ)** | Ресурсы, часто отклоняемые пользователем |

### Принцип работы

- **Выбор пользователя, не автообнаружение**: при срабатывании запроса пользователю пользователь выбирает, добавлять ли ресурс в кэш.
- **Сопоставление префиксов**: поддержка сопоставления префиксов пути ресурса (например, `network:api.example.com/*`).
- **Приоритет**: HighDeny имеет приоритет над HighAllow.
- **Только в памяти**: кэш не персистентен. Теряется при перезапуске.
- **Настраиваемое истечение**: пользователь может установить срок действия записей кэша.

### Процесс обновления кэша

1. Обратный вызов разрешений возвращает `AskUser`.
2. Система разрешений отправляет запрос в карточную систему (Web UI или мгновенные сообщения).
3. Пользователь принимает решение (разрешить/отказать) и **выбирает, кэшировать ли**.
4. Карточная система возвращает решение + флаг кэширования.
5. Система разрешений обновляет соответствующий список кэша.
6. Будущие запросы, соответствующие префиксу кэша, разрешаются немедленно.

## Механизм запроса пользователю

Когда проверка разрешений возвращает `AskUser`:

### Web UI: интерактивная карточка

Web-интерфейс немедленно отображает **интерактивную карточку**, показывающую:

- Тип и путь ресурса
- Описание операции
- Кнопки «Разрешить» / «Отказать»
- Опциональные чекбоксы «Всегда разрешать» / «Всегда отказывать» (добавление в кэш частоты)

### Мгновенные сообщения (без поддержки карточек): случайный код

Для платформ обмена сообщениями, не поддерживающих интерактивные карточки:

1. Система генерирует два случайных 6-значных кода: **код разрешения** и **код отказа**.
2. Отправляется сообщение с информацией о ресурсе и двумя кодами.
3. Пользователь должен ответить точным кодом разрешения для авторизации. Любой другой ответ считается отказом.
4. Коды одноразовые для предотвращения атак повторного воспроизведения.

### Тайм-аут

- Для всех запросов пользователю устанавливается тайм-аут.
- При тайм-ауте запрос считается **отклонённым**, блокировка потока Исполнителя снимается.

## Безопасность динамической компиляции

Самоэволюция (переписывание классов) создаёт уникальные риски безопасности. Система использует **многоуровневую стратегию** для их смягчения:

### Уровень 1: Контроль ссылок при компиляции (основная защита)

- Компилятор получает только **разрешённый список ссылок на сборки**.
- **Разрешено**: `System.Runtime`, `System.Private.CoreLib`, сборки проекта (интерфейс ITool и др.)
- **Заблокировано**: `System.IO`, `System.Reflection`, `System.Runtime.InteropServices` и др.
- Если код ссылается на заблокированную сборку, **сам компилятор отклоняет** код.
- Это надёжнее, чем сканирование во время выполнения — опасные операции невозможны на уровне типов.

### Уровень 2: Статический анализ во время выполнения (вторичная защита)

- Даже после успешной компиляции код проходит статическое сканирование паттернов.
- Обнаружение опасных паттернов операций (прямой I/O, системные вызовы и др.).
- При обнаружении опасного кода загрузка отклоняется, система откатывается к функциональности по умолчанию.

### Ограничения наследования

Все пользовательские классы Кремниевых Существ **должны** наследовать `SiliconBeingBase`. Компилятор принудительно обеспечивает это ограничение на уровне типов.

### Шифрованное хранение

Скомпилированный код хранится на диске в зашифрованном виде AES-256:

- **Получение ключа**: из GUID существа (в верхнем регистре) с использованием PBKDF2.
- **Ошибка дешифрования**: откат к реализации по умолчанию.
- **Перекомпиляция во время выполнения**: новый код сначала компилируется в памяти; персистентность зашифрованного кода происходит только после успешной компиляции и замены экземпляра.

### Атомная замена

Процесс замены является атомарным:

1. Компиляция нового кода в памяти → получение `Type`.
2. Создание нового экземпляра из `Type`.
3. Миграция состояния из старого экземпляра в новый.
4. Обмен ссылками.
5. Персистентность зашифрованного кода.

Если любой шаг завершается неудачей, старый экземпляр остаётся активным.

## Функция обратного вызова разрешений

### Дизайн

Каждый PermissionManager содержит **переменную функции обратного вызова**:

- **По умолчанию**: указывает на встроенную функцию разрешений по умолчанию.
- **После динамической компиляции**: заменяется пользовательской функцией разрешений существа.
- **Одна из двух**: в любой момент времени активен только один обратный вызов.
- **Ошибка компиляции**: не влияет на текущий обратный вызов — по умолчанию или последняя успешная пользовательская функция остаётся действующей.

### Сигнатура обратного вызова

```
PermissionResult Callback(PermissionType type, string resourcePath, Guid callerId)
```

Возвращает `Allowed`, `Denied` или `AskUser`.

## Аудитный журнал

Все решения о разрешениях регистрируются:

```
[2026-04-01 15:30:25] ALLOWED  | Being:AssistantA | Type:NetworkAccess | Resource:api.github.com | Source:HighAllowCache
[2026-04-01 15:30:26] DENIED   | Being:AssistantB | Type:FileAccess    | Resource:C:\Windows\System32 | Source:HighDenyCache
[2026-04-01 15:30:27] ASK_USER | Being:Curator    | Type:CommandLine   | Resource:del /f /q *.log | Source:Callback
[2026-04-01 15:30:28] ALLOWED  | Being:Curator    | Type:CommandLine   | Resource:del /f /q *.log | Source:UserDecision
```

Журналы персистентны в хранилище и доступны для просмотра через Web UI (контроллер журналов).

## Аудит Использования Токенов

`TokenUsageAuditManager` обеспечивает отслеживание потребления AI-токенов, связанное с безопасностью:

- **Запись каждого запроса** — при каждом AI-вызове записывается ID существа, модель, токены подсказки, токены дополнения и метка времени.
- **Обнаружение аномалий** — необычные паттерны потребления токенов могут указывать на инъекцию подсказок или злоупотребление ресурсами.
- **Доступ только для Куратора** — `TokenAuditTool` (помечен `[SiliconManagerOnly]`) позволяет Куратору запрашивать и сводить использование токенов.
- **Веб-панель** — `UsageController` предоставляет браузерную панель с графиками трендов и экспортом данных.
- **Персистентное хранение** — записи хранятся через `ITimeStorage` для запросов временных рядов и долгосрочного анализа.

## Безопасность плагинов

Система плагинов создаёт риски безопасности, связанные с выполнением стороннего кода, которые смягчаются следующими механизмами:

### Песочница безопасности

`PluginLoader` выполняет строгую проверку безопасности при загрузке плагинов:

1. **Проверка запрещённых пространств имён** — плагины не могут ссылаться на следующие пространства имён:
   - `System.IO` — доступ к файловой системе
   - `System.Net.Http` — HTTP-запросы
   - `System.Net.WebSockets` — WebSocket-соединения
   - `System.Net.Sockets` — необработанные сокеты
   - `Microsoft.CodeAnalysis` — API компилятора

2. **Белый список доверенных сборок** — ссылки на следующие сборки разрешены:
   - `Google.Protobuf`, `Newtonsoft.Json`, `MessagePack`
   - `Serilog`, `Microsoft.Extensions.Logging.Abstractions`
   - `Dapper`

3. **Проверка запрещённых типов** — сканирование опасных типов, на которые ссылается плагин

4. **Проверка запрещённых членов** — сканирование опасных методов, вызываемых плагином

### Изолированная загрузка

- Использование пользовательского `AssemblyLoadContext` для изолированной загрузки каждого плагина
- Типы и сборки плагинов не влияют друг на друга
- При выгрузке плагина могут быть освобождены связанные ресурсы

### Ограничения разрешений инструментов

- Инструменты, регистрируемые плагинами через интерфейс `ITool`, подчиняются той же системе разрешений
- Инструменты плагинов не могут обойти цепочку проверки разрешений
- Инструменты плагинов подчиняются атрибуту `[SiliconManagerOnly]`

## Безопасность разрешений инструментов

Система разрешений инструментов предоставляет дополнительный уровень безопасности, контролируя, какие операции инструментов могут использовать Кремниевые Существа:

### Двухуровневая изоляция разрешений

1. **Уровень Кремниевого Существа** — каждое Кремниевое Существо имеет независимую конфигурацию разрешений инструментов
2. **Уровень проекта** — разрешения инструментов в проектном пространстве независимы от уровня Кремниевого Существа, обеспечивая изоляцию разрешений между проектами

### Шаблоны разрешений

Система предоставляет предопределённые шаблоны разрешений для обеспечения базового уровня безопасности:

- **readonly** — минимальные полномочия, разрешены только операции чтения
- **restricted** — ограниченные полномочия, разрешены только базовые операции
- **full** — полные полномочия (используется только Куратором)

### Характеристики безопасности

- **Отказ по умолчанию** — операции инструментов, явно не разрешённые, по умолчанию отклоняются
- **Гранулярность операций** — каждая операция каждого инструмента контролируется независимо (например, `network:get` разрешено, но `network:post` отказано)
- **Управление Куратором** — разрешения инструментов могут быть настроены только Кремниевым Куратором
- **Аудитный след** — изменения разрешений инструментов записываются в аудитный журнал

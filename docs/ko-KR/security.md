# 보안 설계

> **버전: v0.2.0-alpha**

[English](../en/security.md) | [Deutsch](../de-DE/security.md) | [中文](../zh-CN/security.md) | [繁體中文](../zh-HK/security.md) | [Español](../es-ES/security.md) | [日本語](../ja-JP/security.md) | **한국어** | [Čeština](../cs-CZ/security.md) | [Русский](../ru-RU/security.md)

## 개요

실리콘 라이프 콜렉티브의 보안은 **다층 방어** 모델 위에 구축됩니다. 핵심 원칙: **모든 I/O 작업은 이그제큐터를 통과해야 하며**, 이그제큐터는 실행 전 퍼미션 검사를 강제합니다.

```
툴 콜 → 이그제큐터 → 퍼미션 매니저 → 빈도 캐시 → 콜백 → (IsCurator: 사용자 확인 | Non-curator: 글로벌 ACL)
```

---

## 퍼미션 모델

### 퍼미션 타입

| 타입 | 설명 |
|------|------|
| `NetworkAccess` | 아웃바운드 HTTP/HTTPS 요청 |
| `CommandLine` | 셸 명령 실행 |
| `FileAccess` | 파일 및 디렉토리 작업 |
| `Function` | 민감한 함수 호출 |
| `DataAccess` | 시스템 또는 사용자 데이터 접근 |

### 퍼미션 리절트

각 퍼미션 검사는 세 가지 결과 중 하나를 반환합니다:

| 결과 | 동작 |
|------|------|
| **Allowed (허용)** | 작업 즉시 진행 |
| **Denied (거부)** | 작업 차단, 감사 로그 기록 |
| **AskUser (사용자 확인)** | 작업 일시중지, 사용자 확인 필요 |

### 특수 역할: 실리콘 큐레이터

실리콘 큐레이터는 최고 권한 수준(`IsCurator = true`)을 가집니다. 퍼미션 체인이 분기 판단에 도달하면, 큐레이터의 작업은 허용으로 직접 단락되는 대신 `IPermissionAskHandler`를 통해 사용자 확인을 요청합니다. 비큐레이터는 글로벌 ACL을 쿼리합니다.

### 전용 퍼미션 매니저

각 실리콘 비잉은 자체 **전용 PermissionManager** 인스턴스를 가집니다. 퍼미션 상태는 비잉 간에 공유되지 않습니다.

## 퍼미션 검증 프로세스

쿼리 우선순위: **1. 빈도 캐시 → 2. 콜백 함수 → 3. 분기 판단 (IsCurator/GlobalACL)**

```
┌─────────────┐
│ 툴 콜       │
└──────┬──────┘
       │
       ▼
┌─────────────┐     ┌─────────────────────┐
│  이그제큐터  │────▶│ 전용 퍼미션        │
│(디스크/네트워크│     │ 매니저(각 비잉)     │
│  명령줄...)  │     └────────┬────────────┘
└─────────────┘            │
                           ▼
                  ┌─────────────────┐
                  │ 1. 빈도 캐시     │──일치──▶ 허용 / 거부
                  │(HighDeny가       │
                  │  HighAllow보다   │
                  │  우선)           │
                  └────────┬────────┘
                           │ 불일치
                           ▼
                  ┌─────────────────┐
                  │ 2. 퍼미션       │──▶ 허용 / 거부 / 사용자 확인
                  │  콜백 함수       │
                  └────────┬────────┘
                           │ 사용자 확인
                           ▼
                  ┌─────────────────┐
                  │ 3. IsCurator?   │
                  └────────┬────────┘
                           │
                 ┌─────────┴─────────┐
                 │                   │
                 ▼ 예                ▼ 아니오
          ┌─────────────┐    ┌─────────────┐
          │ 사용자 확인  │    │ 글로벌 ACL   │
          │(AskHandler) │    │ 규칙 쿼리    │
          └─────────────┘    └─────────────┘
```

**핵심 사항**: 이그제큐터는 불리언 값(허용/거부)만 봅니다. 퍼미션 매니저는 내부적으로 삼항 결정(허용/거부/사용자 확인)을 처리하며, 이그제큐터에 반환하기 전에 사용자 확인을 해결합니다.

## 이그제큐터 (보안 경계)

이그제큐터는 I/O 작업의 **유일한** 경로입니다. 다음을 강제합니다:

### 독립 스케줄링 스레드

각 이그제큐터는 **독립 스케줄링 스레드**를 가집니다:

- 이그제큐터 간 스레드 격리 — 한 이그제큐터의 스레드 블로킹이 다른 이그제큐터에 영향을 미치지 않음.
- 각 이그제큐터는 독립적인 리소스 제한 설정 가능 (CPU, 메모리 등).
- 이그제큐터 스레드의 스레드 풀 관리.

### 요청 큐

각 이그제큐터는 요청 큐를 유지합니다:

- 요청은 타입에 따라 해당 이그제큐터로 라우팅.
- 우선순위 큐 지원.
- 요청별 타임아웃 제어.

### 퍼미션 검증의 스레드 락

툴이 리소스 접근을 시작할 때:

1. 이그제큐터가 요청을 받고 **스레드를 락**.
2. 이그제큐터가 비잉의 전용 퍼미션 매니저에 쿼리.
3. 콜백이 사용자 확인을 반환하면, 이그제큐터 스레드는 사용자 응답을 기다리며 **락 유지**.
4. 비잉은 최종 결과(성공 또는 거부)만 봅니다 — 중간 "대기 중" 또는 "처리 중" 상태를 절대 보지 못합니다.
5. 실리콘 큐레이터만 실제 사용자 프롬프트를 트리거합니다. 일반 비잉은 블로킹 없이 글로벌 ACL을 동기적으로 쿼리합니다.
6. 타임아웃 시, 요청은 거부로 처리되고 스레드 락이 해제됩니다.

### 이그제큐터 타입

| 이그제큐터 | 범위 | 기본 타임아웃 |
|----------|------|------|
| `DiskExecutor` | 파일 읽기/쓰기, 디렉토리 작업 | 30초 |
| `NetworkExecutor` | HTTP 요청, WebSocket 연결 | 60초 |
| `CommandLineExecutor` | 셸 명령 실행 | 120초 |

> **참고**: `DynamicCompilationExecutor`(`SiliconLife.Core.Compilation` 네임스페이스에 위치)는 Roslyn 메모리 컴파일을 담당하며, I/O 이그제큐터 범주에 속하지 않지만 동일하게 퍼미션 시스템의 제약을 받습니다.

### 예외 격리 및 내고장성

- 한 이그제큐터의 예외가 다른 이그제큐터에 영향을 미치지 않음.
- 스레드 충돌 시 자동 재시작.
- 서킷 브레이커: 연속 실패 후 이그제큐터 일시 중지로 연쇄 실패 방지.

## 글로벌 ACL (접근 제어 목록)

저장소에 영속화된 공유 규칙 테이블, 실리콘 큐레이터만 관리:

```json
{
  "rules": [
    { "prefix": "network:api.github.com", "result": "Allowed" },
    { "prefix": "file:C:\\Windows", "result": "Denied" },
    { "prefix": "cli:rm -rf", "result": "Denied" }
  ]
}
```

- 규칙은 순서대로 평가; 첫 번째 일치가 승리.
- 실리콘 큐레이터만 글로벌 ACL 수정 가능 (전용 툴 통해).
- 변경사항 즉시 적용.
- 글로벌 ACL은 위의 각 쿼리 우선순위 체인에 **없음** — 내부적으로 콜백 함수에 의해 참조됨.

## 사용자 빈도 캐시

반복적인 퍼미션 프롬프트를 줄이기 위해, 시스템은 두 개의 **비잉별, 메모리 전용** 캐시를 유지합니다:

| 캐시 | 용도 |
|------|------|
| **HighAllow (고빈도 허용)** | 사용자가 자주 허용한 리소스 |
| **HighDeny (고빈도 거부)** | 사용자가 자주 거부한 리소스 |

### 작동 방식

- **사용자 선택, 자동 감지 아님**: 사용자 확인이 트리거될 때, 사용자가 리소스를 캐시에 추가할지 선택.
- **접두사 매칭**: 리소스 경로 접두사 매칭 지원 (예: `network:api.example.com/*`).
- **우선순위**: HighDeny가 HighAllow보다 우선순위 높음.
- **메모리 전용**: 캐시는 영속화되지 않음. 재시작 시 손실.
- **구성 가능한 만료**: 사용자가 캐시 항목의 유효 기간 설정 가능.

### 캐시 업데이트 프로세스

1. 퍼미션 콜백이 `AskUser` 반환.
2. 퍼미션 시스템이 카드 시스템(Web UI 또는 인스턴트 메시징)에 쿼리 전송.
3. 사용자가 결정(허용/거부)을 내리고 **캐시 여부 선택**.
4. 카드 시스템이 결정 + 캐시 플래그 반환.
5. 퍼미션 시스템이 해당 캐시 목록 업데이트.
6. 향후 캐시 접두사와 일치하는 요청 즉시 해결.

## 사용자 확인 메커니즘

퍼미션 검사가 `AskUser`를 반환할 때:

### Web UI: 인터랙티브 카드

웹 프론트엔드가 즉시 **인터랙티브 카드**를 표시합니다:

- 리소스 타입 및 경로
- 작업 설명
- 허용 / 거부 버튼
- 선택적 "항상 허용" / "항상 거부" 체크박스 (빈도 캐시에 추가)

### 인스턴트 메시징 (카드 지원 없음): 랜덤 코드

인터랙티브 카드를 지원하지 않는 메시징 플랫폼의 경우:

1. 시스템이 두 개의 6자리 랜덤 코드 생성: **허용 코드** 및 **거부 코드**.
2. 리소스 정보와 두 코드를 포함한 메시지 전송.
3. 사용자가 정확한 허용 코드로 응답해야 승인. 다른 모든 응답은 거부로 처리.
4. 코드는 일회용으로, 재생 공격 방지.

### 타임아웃

- 모든 사용자 확인 요청에 타임아웃 설정.
- 타임아웃 시, 요청은 **거부**로 처리되고 이그제큐터 스레드 락 해제.

## 동적 컴파일 보안

자가 진화(클래스 재작성)는 독특한 보안 위험을 초래합니다. 시스템은 **계층적 전략**으로 이를 완화합니다:

### 1단계: 컴파일 타임 참조 제어 (주요 방어)

- 컴파일러는 **허용된 어셈블리 참조 목록**만 받음.
- **허용**: `System.Runtime`, `System.Private.CoreLib`, 프로젝트 어셈블리 (ITool 인터페이스 등)
- **차단**: `System.IO`, `System.Reflection`, `System.Runtime.InteropServices` 등
- 코드가 차단된 어셈블리를 참조하면, **컴파일러 자체가 코드 거부**.
- 런타임 스캔보다 더 안정적 — 위험한 작업이 타입 레벨에서 불가능.

### 2단계: 런타임 정적 분석 (보조 방어)

- 성공적인 컴파일 후에도, 코드는 정적 패턴 스캔 대상.
- 위험한 작업 패턴 감지 (직접 I/O, 시스템 호출 등).
- 위험한 코드 발견 시, 로딩 거부, 시스템이 기본 기능으로 폴백.

### 상속 제약

모든 커스텀 실리콘 비잉 클래스는 `SiliconBeingBase`를 **상속해야 합니다**. 컴파일러가 타입 레벨에서 이 제약을 강제합니다.

### 암호화 저장

컴파일된 코드는 디스크에 AES-256으로 암호화되어 저장:

- **키 파생**: 비잉의 GUID(대문자)에서 PBKDF2를 사용하여 파생.
- **복호화 실패**: 기본 구현으로 폴백.
- **런타임 재컴파일**: 새 코드는 먼저 메모리에서 컴파일; 성공적인 컴파일 및 인스턴스 교체 후에만 영속화.

### 아토믹 교체

교체 프로세스는 아토믹입니다:

1. 메모리에서 새 코드 컴파일 → `Type` 획득.
2. `Type`에서 새 인스턴스 생성.
3. 이전 인스턴스에서 새 인스턴스로 상태 마이그레이션.
4. 참조 교환.
5. 암호화된 코드 영속화.

어떤 단계든 실패하면, 이전 인스턴스가 활성 상태 유지.

## 퍼미션 콜백 함수

### 설계

각 PermissionManager는 **콜백 함수 변수**를 보유:

- **기본**: 내장 기본 퍼미션 함수를 가리킴.
- **동적 컴파일 후**: 비잉의 커스텀 퍼미션 함수로 재정의.
- **둘 중 하나**: 언제든지 하나의 콜백만 활성.
- **컴파일 실패**: 현재 콜백에 영향 없음 — 기본 또는 마지막으로 성공한 커스텀 함수 유지.

### 콜백 시그니처

```
PermissionResult Callback(PermissionType type, string resourcePath, Guid callerId)
```

`Allowed`, `Denied` 또는 `AskUser` 반환.

## 감사 로그

모든 퍼미션 결정이 기록됩니다:

```
[2026-04-01 15:30:25] ALLOWED  | Being:AssistantA | Type:NetworkAccess | Resource:api.github.com | Source:HighAllowCache
[2026-04-01 15:30:26] DENIED   | Being:AssistantB | Type:FileAccess    | Resource:C:\Windows\System32 | Source:HighDenyCache
[2026-04-01 15:30:27] ASK_USER | Being:Curator    | Type:CommandLine   | Resource:del /f /q *.log | Source:Callback
[2026-04-01 15:30:28] ALLOWED  | Being:Curator    | Type:CommandLine   | Resource:del /f /q *.log | Source:UserDecision
```

로그는 저장소에 영속화되며, Web UI(로그 컨트롤러)를 통해 볼 수 있습니다.

## 토큰 사용 감사

`TokenUsageAuditManager`는 보안 관련 AI 토큰 소모 추적을 제공합니다:

- **요청별 기록** — 각 AI 호출이 비잉 ID, 모델, 프롬프트 토큰, 컴플리션 토큰 및 타임스탬프 기록.
- **이상 감지** — 비정상적인 토큰 소모 패턴은 프롬프트 인젝션 또는 리소스 남용을 나타낼 수 있음.
- **큐레이터 전용 접근** — `TokenAuditTool`(`[SiliconManagerOnly]` 표시)은 큐레이터가 토큰 사용 쿼리 및 집계 가능.
- **웹 대시보드** — `UsageController`는 추세 차트 및 데이터 내보내기가 포함된 브라우저 기반 대시보드 제공.
- **영속화 저장** — 기록은 `ITimeStorage`를 통해 저장되어, 시계열 쿼리 및 장기 분석 가능.

## 플러그인 보안

플러그인 시스템은 서드파티 코드 실행의 보안 위험을 도입하며, 다음 메커니즘으로 완화됩니다:

### 보안 샌드박스 및 역량 선언

`PluginLoader`는 플러그인 로딩 시 보안 스캔을 실행하며, 동시에 역량 선언 메커니즘을 지원합니다:

1. **선언 가능한 역량** — 플러그인이 `[PluginCapability]` 속성으로 필요한 역량을 선언합니다:
   - `Network` — 네트워크 접근(`System.Net.Http`, `System.Net.WebSockets`, `System.Net.Sockets` 참조 허용)
   - `FileIO` — 파일 읽기/쓰기(`System.IO` 참조 허용)
   - `Process` — 프로세스 관리
   - `AI` — AI 호출

2. **선언 불가능한 역량** — 다음 역량은 항상 차단됩니다:
   - P/Invoke (`System.Runtime.InteropServices`)
   - Unsafe 코드 (`System.Runtime.CompilerServices.Unsafe`)
   - Reflection Emit (`System.Reflection.Emit`)
   - 컴파일러 API (`Microsoft.CodeAnalysis`)

3. **신뢰할 수 있는 어셈블리 화이트리스트** — 다음 어셈블리의 참조가 허용됩니다:
   - `Google.Protobuf`, `Newtonsoft.Json`, `MessagePack`
   - `Serilog`, `Microsoft.Extensions.Logging.Abstractions`
   - `Dapper`

4. **금지 타입 검사** — 플러그인에서 참조하는 위험한 타입 스캔

5. **금지 멤버 검사** — 플러그인에서 호출하는 위험한 메서드 스캔

### 격리 로딩

- 각 플러그인은 커스텀 `AssemblyLoadContext`로 격리하여 로딩
- 플러그인 간의 타입 및 어셈블리가 서로 간섭하지 않음
- 플러그인 언로드 시 관련 리소스 해제 가능

### 툴 퍼미션 제약

- 플러그인이 `ITool` 인터페이스를 통해 등록한 툴은 동일한 퍼미션 시스템의 제약을 받음
- 플러그인 툴은 퍼미션 검증 체인을 우회할 수 없음
- 플러그인 툴은 `[SiliconManagerOnly]` 마크의 제약을 받음

## 툴 퍼미션 보안

툴 퍼미션 시스템은 실리콘 비잉이 사용할 수 있는 툴 작업을 제어하는 추가 보안 계층을 제공합니다:

### 2단계 퍼미션 격리

1. **실리콘 비잉 레벨** — 각 실리콘 비잉은 독립적인 툴 퍼미션 설정
2. **프로젝트 레벨** — 프로젝트 공간 내의 툴 퍼미션은 실리콘 비잉 레벨과 독립적, 프로젝트 간 퍼미션 격리 실현

### 퍼미션 템플릿

시스템은 사전 정의된 퍼미션 템플릿을 제공하여 보안 베이스라인을 보장합니다:

- **readonly** — 최소 권한, 읽기 작업만 허용
- **restricted** — 제한된 권한, 기본 작업만 허용
- **full** — 전체 권한 (큐레이터만 사용)

### 보안 특성

- **기본 거부** — 명시적으로 허용되지 않은 툴 작업은 기본적으로 거부
- **작업 세분성** — 각 툴의 각 작업을 독립적으로 제어 (예: `network:get`은 허용하지만 `network:post`는 거부)
- **큐레이터 관리** — 툴 퍼미션은 실리콘 큐레이터만 구성 가능
- **감사 추적** — 툴 퍼미션 변경이 감사 로그에 기록

## 스킬 보안

스킬 시스템은 툴 퍼미션 체계를 재사용하며, 다중 가드레일을 제공합니다:

### 실행 퍼미션

- 스킬 id를 툴명으로 사용하여 `execute` 액션으로 `ToolActionPermissionConfig` 퍼미션 매트릭스에 포함
- 비활성화된 스킬은 AI 가시 툴 정의에 나타나지 않음 (Schema 레이어 필터링 + 런타임 재검사 이중 보장)
- 큐레이터는 항상 실행 가능; 일반 비잉은 `IsActionAllowed(skillId, "execute")` 필요

### 툴 화이트리스트와 퍼미션 합집합

- 스킬 실행 중에는 `ToolWhitelist` 내의 툴만 허용 (빈 목록 = 비잉의 전체 툴 상속)
- 스킬의 액션 제한과 비잉 퍼미션의 **엄격한 측 합집합** (`MergePermissions`): 스킬은 퍼미션을 추가로 좁히기만 하며, 퍼미션을 확장할 수 없음
- 화이트리스트 외의 툴 콜은 즉시 실패 (`Tool not in whitelist`)

### 리소스 소모 가드레일

- **글로벌 스위치**: `SkillEnabled`로 전체 스킬 시스템을 원클릭 비활성화
- **수량 할당량**: 각 비잉의 커스텀 스킬 수는 `MaxCustomSkillsPerBeing` (기본 50) 제한
- **라운드 제한**: `maxToolRound = Min(스킬 선언값, GlobalMaxToolRound 기본 10)`, 제어 불능 루프 방지
- **타임아웃 제한**: `timeout = Min(스킬 선언값, GlobalSkillTimeoutSeconds 기본 300s)`
- **재귀 방지**: 스킬 실행 중 자기 자신을 다시 호출할 수 없음

### 수정 퍼미션

- 큐레이터는 모든 스킬 수정 가능; 일반 비잉은 출처가 `Being`/`User`인 스킬만 수정 가능
- 메타데이터 자동 보완은 누락된 필드만 채우며, 사용자가 제공한 필드는 AI에 의해 덮어쓰지 않음

## MCP 보안

MCP 통합은 "사용자 주권 + 퍼미션 일관성" 원칙을 따릅니다:

### 사용자 주권

- MCP 서버의 추가, 삭제, 활성화/비활성화, 재연결은 **사용자가 Web UI** (/mcp 또는 설정 페이지)를 통해서만 수행
- AI 측의 `mcp` 툴은 읽기 전용 쿼리 (status/list_servers/list_tools)이며, 서버 목록을 수정할 수 없음
- `McpEnabled` 글로벌 스위치로 모든 외부 툴을 원클릭 차단 가능

### 툴 격리와 퍼미션

- 래핑 툴은 `mcp_{serverId}_{toolName}`으로 명명되며, 내장/플러그인 툴 네임스페이스와 격리
- 각 래핑 툴은 자동으로 단일 `execute` 액션을 선언하여 2단계 툴 퍼미션 매트릭스에 포함, 비잉/프로젝트별로 개별 비활성화 가능
- 서버 비활성화 시 해당 툴이 모든 비잉에서 즉시 등록 해제

### 전송과 프로세스 경계

- `stdio` 서버는 서브프로세스로 실행되며, 명시적으로 설정된 환경 변수 (`env` 필드)만 상속
- `http` 서버는 설정된 엔드포인트를 통해 통신, 연결 실패 시 자동으로 error 상태로 전환되고 `lastError` 노출

## IM 시크릿 보안

### 환경 변수 플레이스홀더

IM 플랫폼 설정 값은 `${ENV_VAR}` 플레이스홀더를 지원합니다 (예: `"${FEISHU_APP_SECRET}"`):

- `ConfigSecretResolver`는 **딥카피 복사본**에서 플레이스홀더를 해석하며, 원본 `config.json`은 항상 플레이스홀더 원형 유지
- 후속 `SaveConfig`는 해석된 평문 시크릿을 디스크에 기록하지 않음
- 정수 플레이스홀더와 값 내장 플레이스홀더 (예: `prefix-${VAR}`) 지원

### OAuth 인증 보안

- **state CSRF 방지**: 16바이트 암호화 난수, 콜백 시 엄격 검증
- **5분 타임아웃**: 인증 세션 타임아웃 시 자동 무효화, 이전 세션이 덮어씌워질 때 즉시 취소
- **토큰 저장**: accessToken/refreshToken/tokenExpiresAt을 플랫폼 설정에 기록하고 영속화, `authMode`를 `oauth`로 표시
- 콜백 URL은 `redirectBaseUrl` 설정 지원 (공용 네트워크 콜백 시나리오)

### 메시지 보안

- Feishu: 서명 검증 (`X-Lark-Signature`, SHA256) + AES-256-CBC 이벤트 복호화 + 이벤트 중복 제거 (10분 윈도우)
- WeChat Enterprise: WXBizMsgCrypt 암호화/복호화 및 서명 검증
- DingTalk: Stream 모드는 암호화 WebSocket 사용; HTTP 모드는 콜백 검증

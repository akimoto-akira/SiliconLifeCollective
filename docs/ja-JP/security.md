# セキュリティ設計

> **バージョン: v0.2.0-alpha**

[English](../en/security.md) | [Deutsch](../de-DE/security.md) | [中文](../zh-CN/security.md) | [繁體中文](../zh-HK/security.md) | [Español](../es-ES/security.md) | **日本語** | [한국어](../ko-KR/security.md) | [Čeština](../cs-CZ/security.md) | [Русский](../ru-RU/security.md)

## 概要

シリコンライフコレクティブのセキュリティは**多層防御**モデルに基づいています。コア原則：**すべての I/O 操作はエグゼキューターを経由する必要があり**、エグゼキューターは実行前にパーミッションチェックを強制します。

```
ツールコール → エグゼキューター → パーミッションマネージャー → 高頻度キャッシュ → コールバック → (IsCurator: ユーザーに確認 | 非キュレーター: グローバルACL)
```

---

## パーミッションモデル

### パーミッションタイプ

| タイプ | 説明 |
|------|-------------|
| `NetworkAccess` | 送信 HTTP/HTTPS リクエスト |
| `CommandLine` | シェルコマンド実行 |
| `FileAccess` | ファイルおよびディレクトリ操作 |
| `Function` | 機密関数呼び出し |
| `DataAccess` | システムまたはユーザーデータへのアクセス |

### パーミッション結果

各パーミッションチェックは3つの結果のいずれかを返します：

| 結果 | 動作 |
|--------|----------|
| **Allowed（許可）** | 操作は直ちに進行 |
| **Denied（拒否）** | 操作はブロックされ、監査ログに記録 |
| **AskUser（ユーザーに確認）** | 操作は一時停止。ユーザー確認が必要 |

### 特別なロール：シリコンキュレーター

シリコンキュレーターは最高パーミッションレベル（`IsCurator = true`）を持ちます。パーミッションチェーンが分岐判断に達したとき、キュレーターの操作は `IPermissionAskHandler` を通じてユーザー確認を求めます。非キュレーターはグローバル ACL をクエリします。

### プライベートパーミッションマネージャー

各シリコンビーイングは独自の**プライベート PermissionManager** インスタンスを持ちます。パーミッション状態はビーイング間で共有されません。

## パーミッション検証フロー

クエリ優先度：**1. 高頻度キャッシュ → 2. コールバック関数 → 3. 分岐判断（IsCurator/GlobalACL）**

```
┌─────────────┐
│ ツールコール │
└──────┬──────┘
       │
       ▼
┌─────────────┐     ┌─────────────────────┐
│  エグゼ      │────▶│ プライベート         │
│ キューター   │     │ パーミッション       │
│（ディスク/   │     │ マネージャー         │
│ ネット/     │     │（ビーイングごと）    │
│ コマンド...）│     └────────┬────────────┘
└─────────────┘            │
                           ▼
                  ┌─────────────────┐
                  │ 1. 高頻度キャッシュ│──マッチ──▶ 許可 / 拒否
                  │（高拒否は高許可    │
                  │   より優先）       │
                  └────────┬────────┘
                           │ 非マッチ
                           ▼
                  ┌─────────────────┐
                  │ 2. パーミッション │
                  │  コールバック関数 │──▶ 許可 / 拒否 / ユーザーに確認
                  └────────┬────────┘
                           │ ユーザーに確認
                           ▼
                  ┌─────────────────┐
                  │ 3. IsCurator?   │
                  └────────┬────────┘
                           │
                 ┌─────────┴─────────┐
                 │                   │
                 ▼ はい              ▼ いいえ
          ┌─────────────┐    ┌─────────────┐
          │ ユーザー確認  │    │ グローバルACL │
          │（AskHandler）│    │ ルールクエリ  │
          └─────────────┘    └─────────────┘
```

**重要ポイント**：エグゼキューターはブール値（許可/拒否）のみを見ます。パーミッションマネージャーは内部的に三者択一の決定（許可/拒否/ユーザーに確認）を処理し、エグゼキューターに返す前に「ユーザーに確認」を解決します。

## エグゼキューター（セキュリティ境界）

エグゼキューターは I/O 操作の**唯一**のパスです。以下を強制します：

### 独立スケジューリングスレッド

各エグゼキューターは**独立したスケジューリングスレッド**を持ちます：

- エグゼキューター間のスレッド分離 — あるエグゼキューターのスレッドがブロックされても他のエグゼキューターに影響しません。
- 各エグゼキューターは独立したリソース制限（CPU、メモリなど）を設定可能。
- エグゼキュータースレッドのスレッドプール管理。

### リクエストキュー

各エグゼキューターはリクエストキューを維持します：

- リクエストはタイプに応じて対応するエグゼキューターにルーティング。
- 優先度付きキューイングをサポート。
- リクエストごとのタイムアウト制御。

### パーミッション検証のスレッドロック

ツールがリソースアクセスを開始した場合：

1. エグゼキューターはリクエストを受け取り、**そのスレッドをロック**します。
2. エグゼキューターはビーイングのプライベートパーミッションマネージャーにクエリします。
3. コールバックが「ユーザーに確認」を返した場合、エグゼキュータースレッドはユーザー応答を待機したまま**ロックを維持**します。
4. ビーイングは最終結果（成功または拒否）のみを見ます — 中間の「保留中」や「待機中」状態を見ることは決してありません。
5. シリコンキュレーターのみが真のユーザープロンプトをトリガーします。通常のビーイングはブロッキングせずにグローバル ACL を同期的にクエリします。
6. タイムアウト時、リクエストは拒否として扱われ、スレッドロックが解放されます。

### エグゼキュータータイプ

| エグゼキューター | 範囲 | デフォルトタイムアウト |
|----------|-------|-----------------|
| `DiskExecutor` | ファイル読み/書き、ディレクトリ操作 | 30秒 |
| `NetworkExecutor` | HTTP リクエスト、WebSocket 接続 | 60秒 |
| `CommandLineExecutor` | シェルコマンド実行 | 120秒 |

> **注意**：`DynamicCompilationExecutor`（`SiliconLife.Core.Compilation` 名前空間に配置）は Roslyn メモリコンパイルを担当し、I/O エグゼキューターの範疇ではありませんが、同様にパーミッションシステムの制約を受けます。

### 例外分離とフォールトトレランス

- 1つのエグゼキューターの例外が他のエグゼキューターに影響しません。
- スレッドクラッシュ時の自動再起動。
- サーキットブレーカー：連続失敗後、エグゼキューターを一時的に停止してカスケード障害を防止。

## グローバル ACL（アクセスコントロールリスト）

ストレージに永続化された共有ルールテーブル。シリコンキュレーターのみが管理：

```json
{
  "rules": [
    { "prefix": "network:api.github.com", "result": "Allowed" },
    { "prefix": "file:C:\\Windows", "result": "Denied" },
    { "prefix": "cli:rm -rf", "result": "Denied" }
  ]
}
```

- ルールは順番に評価。最初のマッチが勝利。
- シリコンキュレーターのみがグローバル ACL を変更可能（専用ツール経由）。
- 変更は直ちに有効。
- グローバル ACL は上記の各クエリの優先度チェーンには含まれません — コールバック関数によって内部的に参照されます。

## ユーザー高頻度キャッシュ

繰り返しパーミッションプロンプトを減らすため、システムは2つの**ビーイングごと、メモリのみ**のキャッシュを維持します：

| キャッシュ | 用途 |
|-------|---------|
| **HighAllow（高許可）** | ユーザーが頻繁に許可するリソース |
| **HighDeny（高拒否）** | ユーザーが頻繁に拒否するリソース |

### 動作原理

- **ユーザー選択、自動検出ではない**：「ユーザーに確認」がトリガーされたとき、ユーザーはリソースをキャッシュに追加するかどうかを選択します。
- **プレフィックスマッチ**：リソースパスプレフィックスマッチをサポート（例：`network:api.example.com/*`）。
- **優先度**：高拒否は高許可よりも優先度が高い。
- **メモリのみ**：キャッシュは永続化されません。再起動時に失われます。
- **設定可能な有効期限**：ユーザーはキャッシュエントリの有効期限を設定可能。

### キャッシュ更新フロー

1. パーミッションコールバックが `AskUser` を返す。
2. パーミッションシステムはカードシステム（Web UI または IM）にクエリを送信。
3. ユーザーは決定（許可/拒否）を下し、**キャッシュするかどうかを選択**。
4. カードシステムは決定 + キャッシュフラグを返す。
5. パーミッションシステムは対応するキャッシュリストを更新。
6. 将来、キャッシュプレフィックスにマッチするリクエストは直ちに解決。

## ユーザー確認メカニズム

パーミッションチェックが `AskUser` を返した場合：

### Web UI：インタラクティブカード

Web フロントエンドは**インタラクティブカード**を直ちに表示します。内容：

- リソースタイプとパス
- 操作の説明
- 許可 / 拒否ボタン
- オプションの「常に許可」/「常に拒否」チェックボックス（高頻度キャッシュに追加）

### IM（カード非対応）：ランダムコード

インタラクティブカードをサポートしないメッセージングプラットフォームの場合：

1. システムは2つのランダム6桁コードを生成：**許可コード**と**拒否コード**。
2. リソース情報と2つのコードを含むメッセージを送信。
3. ユーザーは正確な許可コードを返信して承認する必要があります。その他の返信は拒否として扱われます。
4. コードはワンタイムユース。リプレイ攻撃を防止。

### タイムアウト

- すべての「ユーザーに確認」リクエストにタイムアウトを設定。
- タイムアウト時、リクエストは**拒否**として扱われ、エグゼキューターのスレッドロックが解放されます。

## 動的コンパイルセキュリティ

自己進化（クラスのオーバーライド）は固有のセキュリティリスクをもたらします。システムは**多層戦略**でそれらを緩和します：

### レイヤー 1：コンパイル時参照制御（主要防御）

- コンパイラは**許可されたアセンブリ参照リスト**のみを取得します。
- **許可**：`System.Runtime`、`System.Private.CoreLib`、プロジェクトアセンブリ（ツールインターフェースなど）
- **ブロック**：`System.IO`、`System.Reflection`、`System.Runtime.InteropServices` など
- コードがブロックされたアセンブリを参照した場合、**コンパイラ自体がコードを拒否**します。
- これはランタイムスキャンよりも信頼性が高い — 危険な操作はタイプレベルで不可能です。

### レイヤー 2：ランタイム静的解析（二次防御）

- コンパイル成功後でも、コードは静的パターンスキャンを受けます。
- 危険な操作パターン（直接 I/O、システムコールなど）を検出します。
- 危険なコードが見つかった場合、ロードは拒否され、システムはデフォルト機能にフォールバックします。

### 継承制約

すべてのカスタムシリコンビーイングクラスは**必ず** `SiliconBeingBase` を継承しなければなりません。コンパイラはタイプレベルでこの制約を強制します。

### 暗号化ストレージ

コンパイルされたコードは AES-256 でディスク上に暗号化保存されます：

- **鍵導出**：ビーイングの GUID（大文字）から PBKDF2 を使用。
- **復号失敗**：デフォルト実装にフォールバック。
- **ランタイム再コンパイル**：新しいコードはまずメモリ内でコンパイルされます。コンパイルとインスタンスの置換が成功した場合のみ永続化。

### アトミック置換

置換プロセスはアトミックです：

1. メモリ内で新しいコードをコンパイル → `Type` を取得。
2. `Type` から新しいインスタンスを作成。
3. 古いインスタンスから新しいインスタンスに状態を移行。
4. 参照を交換。
5. 暗号化コードを永続化。

いずれかのステップが失敗した場合、古いインスタンスはアクティブなまま維持されます。

## パーミッションコールバック関数

### 設計

各 PermissionManager は**コールバック関数変数**を持ちます：

- **デフォルト**：組み込みデフォルトパーミッション関数を指します。
- **動的コンパイル後**：ビーイングのカスタムパーミッション関数でオーバーライドされます。
- **二者択一**：いつでもアクティブなコールバックは1つのみ。
- **コンパイル失敗**：現在のコールバックに影響しません — デフォルトまたは前回の成功したカスタム関数が有効なまま。

### コールバックシグネチャ

```
PermissionResult Callback(PermissionType type, string resourcePath, Guid callerId)
```

`Allowed`、`Denied`、または `AskUser` を返す。

## 監査ログ

すべてのパーミッション決定が記録されます：

```
[2026-04-01 15:30:25] ALLOWED  | Being:AssistantA | Type:NetworkAccess | Resource:api.github.com | Source:HighAllowCache
[2026-04-01 15:30:26] DENIED   | Being:AssistantB | Type:FileAccess    | Resource:C:\Windows\System32 | Source:HighDenyCache
[2026-04-01 15:30:27] ASK_USER | Being:Curator    | Type:CommandLine   | Resource:del /f /q *.log | Source:Callback
[2026-04-01 15:30:28] ALLOWED  | Being:Curator    | Type:CommandLine   | Resource:del /f /q *.log | Source:UserDecision
```

ログはストレージに永続化され、Web UI（ログコントローラー）を介して表示可能です。

## トークン使用監査

`TokenUsageAuditManager` はセキュリティ関連の AI トークン消費追跡を提供します：

- **リクエストごとの記録** — 各 AI 呼び出しはビーイング ID、モデル、プロンプトトークン、補完トークン、タイムスタンプを記録。
- **異常検知** — 異常なトークン消費パターンは、プロンプトインジェクションやリソース乱用を示す可能性があります。
- **キュレーターのみアクセス** — `TokenAuditTool`（`[SiliconManagerOnly]` でマーク）は、キュレーターがトークン使用をクエリおよび集計することを許可。
- **Web ダッシュボード** — `UsageController` は、トレンドグラフとデータエクスポート付きのブラウザベースダッシュボードを提供。
- **永続化ストレージ** — 記録は `ITimeStorage` を介して保存。時系列クエリと長期分析用。

## プラグインセキュリティ

プラグインシステムはサードパーティコード実行のセキュリティリスクを導入します。以下のメカニズムで緩和します：

### セキュリティサンドボックスと能力宣言

`PluginLoader` はプラグインのロード時にセキュリティスキャンを実行し、同時に能力宣言メカニズムをサポートします：

1. **宣言可能な能力** — プラグインは `[PluginCapability]` 属性で必要な能力を宣言します：
   - `Network` — ネットワークアクセス（`System.Net.Http`、`System.Net.WebSockets`、`System.Net.Sockets` の参照を許可）
   - `FileIO` — ファイル読み書き（`System.IO` の参照を許可）
   - `Process` — プロセス管理
   - `AI` — AI 呼び出し

2. **宣言不可能な能力** — 以下の能力は常にブロックされます：
   - P/Invoke（`System.Runtime.InteropServices`）
   - Unsafe コード（`System.Runtime.CompilerServices.Unsafe`）
   - Reflection Emit（`System.Reflection.Emit`）
   - コンパイラ API（`Microsoft.CodeAnalysis`）

3. **信頼アセンブリホワイトリスト** — 以下のアセンブリの参照が許可：
   - `Google.Protobuf`、`Newtonsoft.Json`、`MessagePack`
   - `Serilog`、`Microsoft.Extensions.Logging.Abstractions`
   - `Dapper`

4. **禁止型チェック** — プラグイン内で参照される危険な型をスキャン

5. **禁止メンバーチェック** — プラグイン内で呼び出される危険なメソッドをスキャン

### 分離ロード

- カスタム `AssemblyLoadContext` を使用して各プラグインを分離ロード
- プラグイン間の型とアセンブリは互いに干渉しません
- プラグインのアンロード時に関連リソースを解放可能

### ツールパーミッション制約

- プラグインがツールインターフェースを介して登録するツールは、同じパーミッションシステムの制約を受けます
- プラグインツールはパーミッション検証チェーンをバイパスできません
- プラグインツールは `[SiliconManagerOnly]` マークの制約を受けます

## ツールパーミッションセキュリティ

ツールパーミッションシステムは、シリコンビーイングが使用できるツール操作を制御する追加のセキュリティレイヤーを提供します：

### 2レベルパーミッション分離

1. **シリコンビーイングレベル** — 各シリコンビーイングは独立したツールパーミッション設定を持ちます
2. **プロジェクトレベル** — プロジェクト空間内のツールパーミッションはシリコンビーイングレベルから独立し、プロジェクト間のパーミッション分離を実現します

### パーミッションテンプレート

システムは事前定義されたパーミッションテンプレートを提供し、セキュリティベースラインを確保します：

- **readonly** — 最小権限、読み取り操作のみ許可
- **restricted** — 制限付き権限、基本操作のみ許可
- **full** — 完全権限（キュレーターのみ使用）

### セキュリティ機能

- **デフォルト拒否** — 明示的に許可されていないツール操作はデフォルトで拒否
- **操作粒度** — 各ツールの各操作を個別に制御（例：`network:get` は許可、`network:post` は拒否）
- **キュレーター管理** — ツールパーミッションはシリコンキュレーターのみが設定可能
- **監査トレース** — ツールパーミッションの変更は監査ログに記録

---

## スキルセキュリティ

スキルシステムはツールパーミッション体系を再利用し、多層ガードレールを提供します：

### 実行パーミッション

- スキル id はツール名として `execute` アクションで `ToolActionPermissionConfig` パーミッションマトリックスに組み込まれます
- 無効化されたスキルは AI から参照可能なツール定義に表示されません（Schema 層フィルタ + ランタイム再確認の二重保障）
- キュレーターは常に実行可能。通常のビーイングは `IsActionAllowed(skillId, "execute")` が必要です

### ツールホワイトリストとパーミッション和集合

- スキル実行中は `ToolWhitelist` 内のツールのみ許可（空リスト = ビーイングの全ツールを継承）
- スキルのアクション制限とビーイングパーミッションの**厳格側和集合**を取ります（`MergePermissions`）：スキルはパーミッションをさらに絞ることしかできず、権限を拡張することはありません
- ホワイトリスト外のツール呼び出しは直接失敗します（`Tool not in whitelist`）

### リソース消費ガードレール

- **グローバルスイッチ**：`SkillEnabled` でスキルシステム全体をワンクリック無効化
- **数量クォータ**：各ビーイングのカスタムスキル数は `MaxCustomSkillsPerBeing`（デフォルト 50）で制限
- **ラウンド制限**：`maxToolRound = Min(スキル宣言値, GlobalMaxToolRound デフォルト 10)` で暴走ループを防止
- **タイムアウト制限**：`timeout = Min(スキル宣言値, GlobalSkillTimeoutSeconds デフォルト 300s)`
- **再帰防护**：スキル実行中は自身を再呼び出しできません

### パーミッションの変更

- キュレーターはすべてのスキルを変更可能。通常のビーイングはソースが `Being`/`User` のスキルのみ変更可能
- メタデータ自動補完は欠落フィールドのみ埋め、ユーザーが提供したフィールドは AI によって上書きされません

## MCP セキュリティ

MCP 統合は「ユーザー主権 + パーミッション一貫性」の原則に従います：

### ユーザー主権

- MCP サーバーの追加、削除、有効化/無効化、再接続は**ユーザーが Web UI**（/mcp または設定ページ）からのみ実行可能
- AI 側の `mcp` ツールは読み取り専用クエリ（status/list_servers/list_tools）であり、サーバーリストを変更できません
- `McpEnabled` グローバルスイッチで全外部ツールをワンクリック切断可能

### ツール分離とパーミッション

- ラッパーツールは `mcp_{serverId}_{toolName}` という名前で、内蔵/プラグインツールの名前空間と分離
- 各ラッパーツールは自動的に単一の `execute` アクションを宣言し、2レベルツールパーミッションマトリックスに組み込まれ、ビーイング/プロジェクトごとに個別に無効化可能
- サーバー無効化後、そのツールは全ビーイングから即座に登録解除

### トランスポートとプロセス境界

- `stdio` サーバーはサブプロセスとして実行され、明示的に設定された環境変数（`env` フィールド）のみ継承
- `http` サーバーは設定されたエンドポイントを通じて通信し、接続失敗時に自動的に error 状態に移行し `lastError` を公開

## IM キーセキュリティ

### 環境変数プレースホルダー

IM プラットフォーム設定値は `${ENV_VAR}` プレースホルダーをサポートします（例：`"${FEISHU_APP_SECRET}"`）：

- `ConfigSecretResolver` は**ディープコピー**でプレースホルダーを解決し、元の `config.json` は常にプレースホルダーのまま維持
- 後続の `SaveConfig` は解決された平文キーをディスクに書き戻しません
- 値全体のプレースホルダーと値内埋め込みプレースホルダー（例：`prefix-${VAR}`）をサポート

### OAuth 認可セキュリティ

- **state による CSRF 防止**：16バイトの暗号化乱数、コールバック時に厳密に検証
- **5分タイムアウト**：認可セッションはタイムアウトで自動的に無効化され、旧セッションは上書き時に即座にキャンセル
- **トークンストレージ**：accessToken/refreshToken/tokenExpiresAt はプラットフォーム設定に書き戻されて永続化、`authMode` は `oauth` に設定
- コールバック URL は `redirectBaseUrl` 設定をサポート（パブリックネットワークコールバックシナリオ）

### メッセージセキュリティ

- Feishu：署名検証（`X-Lark-Signature`、SHA256）+ AES-256-CBC イベント復号 + イベント重複排除（10分ウィンドウ）
- WeChat Enterprise：WXBizMsgCrypt 加復号と署名検証
- DingTalk：Stream モードは暗号化 WebSocket を使用、HTTP モードはコールバック検証

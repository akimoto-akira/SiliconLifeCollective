## デュアルバージョンアーキテクチャ

本プロジェクトは2つの実装バージョンを提供しており、同じアーキテクチャ設計を共有しながら、ストレージとパフォーマンス最適化の面で異なります：

### SiliconLife.Default（デフォルトバージョン）
- **位置づけ**：デフォルト実装、主にアーキテクチャの実現可能性の検証用
- **実行モード**：コンソールアプリケーション
- **ストレージ方式**：純粋なファイルシステム JSON ストレージ
- **適用シナリオ**：データセキュリティ要件が高い、メモリリソースが制限されている、データ量が少ないシナリオ
- **役割説明**：アーキテクチャ検証のベースライン実装として、シンプルで信頼性の高い実行方法を提供し、本プロジェクトに初めて触れる方、開発デバッグ、データセキュリティ優先のシナリオに適しています

### SiliconLife.Fast（高性能バージョン）
- **位置づけ**：本番推奨バージョン
- **実行モード**：デスクトップアプリケーション（Windows システムトレイ / Linux ステータスウィンドウ）
- **ストレージ方式**：SpeedyPack メモリストレージ + 非同期バッチ永続化（.spk ファイル形式）
- **適用シナリオ**：高同時接続、低遅延、大データ量のシナリオ
- **プラットフォームサポート**：Windows/macOS（フル機能、システムトレイ含む）、Linux（ステータスウィンドウ、トレイアイコンなし）
- **特徴**：
  - Windows/macOS システムトレイでのバックグラウンド実行、トレイステータスウィンドウによるリアルタイム監視；Linux ステータスウィンドウを直接表示
  - SpeedyPack エンジン + 自動圧縮によるデータセキュリティ保証
  - Component UI アーキテクチャ、27 の宣言型コンポーネント
  - 7 種類のスキンテーマ、自動検出と切り替えをサポート
  - ホットリロードツールによるオンライン更新と再起動をサポート → Linux で自動的にブラウザを開き Web UI にアクセス、`--no-tray` パラメータをサポート
  - Linux でのブラウザ自動起動による Web UI アクセス、`--no-tray` パラメータをサポート
- **パフォーマンス向上**：ストレージ読み取り遅延 1000 倍低下、書き込み遅延 15000 倍低下
- **役割説明**：深く最適化された本番級実装であり、システムトレイバックグラウンド実行、SpeedyPack エンジン + 自動圧縮などの機能を備え、長期運用と実際の本番環境における首选です

> **注意**：本ドキュメントで説明するアーキテクチャは両バージョンに適用され、ストレージ実装部分のみが異なります。SiliconLife.Default はアーキテクチャ検証のベースラインとして、SiliconLife.Fast は本番環境の推奨バージョンとして位置づけられています。

## コアコンセプト

### シリコンビーイング

システム内の各 AI エージェントは**シリコンビーイング** —— 自身のアイデンティティ、個性、能力を持つ自律的なエンティティです。各シリコンビーイングは**ソウルファイル**（Markdown プロンプト）によって駆動され、その行動パターンを定義します。

### シリコンキュレーター

**シリコンキュレーター**は、システム内で最高権限を持つ特別なシリコンビーイングです。システム管理者として機能します：

- 他のシリコンビーイングの作成と管理
- ユーザーリクエストの分析とタスクへの分解
- タスクの適切なシリコンビーイングへの割り当て
- 実行品質の監視と障害対応
- **優先スケジューリング**によるユーザーメッセージへの応答（後述）

### ソウルファイル

各シリコンビーイングのデータディレクトリに保存される Markdown ファイル（`soul.md`）。システムプロンプトとして各 AI リクエストに注入され、ビーイングの個性、意思決定パターン、行動制約を定義します。

## スケジューリング：タイムスロットフェアスケジューリング

### メインループ + クロックオブジェクト

システムは専用のバックグラウンドスレッドで**クロック駆動メインループ**を実行します：

```
主循环（专用线程，看门狗 + 熔断器）
  └── 时钟对象 A（优先级=0，间隔=100ms）
  └── 时钟对象 B（优先级=1，间隔=500ms）
  └── 硅基生命体管理器（由主循环直接时钟触发）
        └── 硅基生命体运行器 → 硅基生命体 1 → 时钟触发 → 执行一轮
        └── 硅基生命体运行器 → 硅基生命体 2 → 时钟触发 → 执行一轮
        └── 硅基生命体运行器 → 硅基生命体 3 → 时钟触发 → 执行一轮
        └── ...
```

主要な設計判断：

- **シリコンビーイングはクロックオブジェクトを継承しません。** それらは独自の `Tick()` メソッドを持ち、メインループに直接登録されるのではなく、`SiliconBeingManager` を介して `SiliconBeingRunner` から呼び出されます。
- **シリコンビーイングマネージャー**はメインループから直接クロックトリガーされ、すべてのビーイングの単一エージェントとして機能します。
- **シリコンビーイングランナー**は、一時スレッド上で各ビーイングの `Tick()` をラップし、タイムアウトとビーイングごとのサーキットブレーカー（連続 3 回のタイムアウト → 1 分間のクールダウン）を備えています。
- 各ビーイングの実行は、クロックトリガーごとに AI リクエスト + ツールコール **1 ラウンド**に制限され、どのビーイングもメインループを独占できないことを保証します。
- **パフォーマンスモニター**はクロック実行時間を追跡し、オブザーバビリティを実現します。

### キュレーター優先応答

ユーザーがシリコンキュレーターにメッセージを送信した場合：

1. 現在のビーイング（例：ビーイング A）が現在のラウンドを完了 —— **中断しません**。
2. マネージャーは**残りのキューをスキップ**します。
3. ループは**キュレーターから再開**し、即座に実行されます。

これにより、進行中のタスクを妨げることなく、ユーザーインタラクションに応答できます。

## チャットシステム

### セッションタイプ

チャットシステムは `SessionBase` を通じて3つのセッションタイプをサポートします：

| タイプ | クラス | 説明 |
|------|-------|-------------|
| `SingleChat` | `SingleChatSession` | 2人の参加者間の1対1の会話 |
| `GroupChat` | `GroupChatSession` | 複数参加者のグループチャット |
| `Broadcast` | `BroadcastChannel` | 固定 ID を持つオープンチャンネル；ビーイングが動的にサブスクライブし、サブスクライブ後のメッセージのみを受信 |

### ブロードキャストチャンネル

`BroadcastChannel` は、システム全体のアナウンスに使用される特別なセッションタイプです：

- **固定チャンネル ID** —— `SingleChatSession` や `GroupChatSession` とは異なり、チャンネル ID はメンバーの GUID から派生するものではなく、よく知られた定数です。
- **動的サブスクライブ** —— ビーイングは実行時にサブスクライブ/サブスクライブ解除を行います；サブスクライブ後に公開されたメッセージのみを受信します。
- **保留メッセージフィルタリング** —— `GetPendingMessages()` は、ビーイングのサブスクライブ時刻以降に公開され、まだ読まれていないメッセージのみを返します。
- **チャットシステムによる管理** —— `GetOrCreateBroadcastChannel()`、`Broadcast()`、`GetPendingBroadcasts()`。

### チャットメッセージ

`ChatMessage` モデルには、AI 会話コンテキストとトークン追跡のためのフィールドが含まれています：

| フィールド | 型 | 説明 |
|-------|------|-------------|
| `Id` | `Guid` | 一意のメッセージ識別子 |
| `SenderId` | `Guid` | 送信者の一意識別子 |
| `ChannelId` | `Guid` | チャンネル/会話識別子 |
| `Content` | `string` | メッセージ内容 |
| `Timestamp` | `DateTime` | メッセージ送信時刻 |
| `Type` | `MessageType` | テキスト、画像、ファイル、またはシステム通知 |
| `ReadBy` | `List<Guid>` | このメッセージを読んだ参加者 ID |
| `Role` | `MessageRole` | AI 会話ロール（ユーザー、アシスタント、ツール） |
| `ToolCallId` | `string?` | ツール結果メッセージのツールコール ID |
| `ToolCallsJson` | `string?` | アシスタントメッセージのシリアライズされたツールコール JSON |
| `Thinking` | `string?` | AI の思考連鎖推論 |
| `PromptTokens` | `int?` | プロンプト内のトークン数（入力） |
| `CompletionTokens` | `int?` | 補完内のトークン数（出力） |
| `TotalTokens` | `int?` | 使用された合計トークン数（入力 + 出力） |
| `FileMetadata` | `FileMetadata?` | 添付ファイルのメタデータ（メッセージにファイルが含まれる場合） |

### チャットメッセージキュー

`ChatMessageQueue` は、チャットメッセージの非同期処理を管理するスレッドセーフなメッセージキューシステムです：

- **スレッドセーフ** - ロックメカニズムにより同時アクセスの安全性を確保
- **非同期処理** - 非同期メッセージのエンキューとデキューをサポート
- **メッセージ順序** - メッセージの時系列順序を維持
- **バッチ操作** - バッチでのメッセージ取得をサポート

### ファイルメタデータ

`FileMetadata` は、チャットメッセージに添付されたファイル情報を管理します：

- **ファイル情報** - ファイル名、サイズ、タイプ、パス
- **アップロード時刻** - ファイルのアップロードタイムスタンプ
- **アップロード者** - ファイルをアップロードしたユーザーまたはシリコンビーイング ID

### ストリームキャンセルマネージャー

`StreamCancellationManager` は、AI ストリーミングレスポンスのキャンセルメカニズムを提供します：

- **ストリーム制御** - 進行中の AI ストリーミングレスポンスのキャンセルをサポート
- **リソースクリーンアップ** - キャンセル時に関連リソースを適切にクリーンアップ
- **同時安全性** - 複数のストリームの同時管理をサポート

### チャット履歴表示

新しく追加されたチャット履歴表示機能により、ユーザーはシリコンビーイングの過去の会話を閲覧できます：

- **セッション一覧** - すべての履歴セッションを表示
- **メッセージ詳細** - 完全なメッセージ履歴を表示
- **タイムラインビュー** - 時系列でメッセージを表示
- **API サポート** - セッションとメッセージデータを取得する RESTful API を提供

## AI クライアントシステム

システムは `IAIClient` インターフェースを通じて複数の AI バックエンドをサポートします：

### OllamaClient

- **タイプ**：ローカル AI サービス
- **プロトコル**：ネイティブ Ollama HTTP API（`/api/chat`、`/api/generate`）
- **機能**：ストリーミング、ツールコール、ローカルモデルホスティング
- **設定**：`endpoint`、`model`、`temperature`、`maxTokens`

### DashScopeClient（Alibaba Cloud Bailian）

- **タイプ**：クラウド AI サービス
- **プロトコル**：OpenAI 互換 API（`/compatible-mode/v1/chat/completions`）
- **認証**：Bearer トークン（API キー）
- **機能**：ストリーミング、ツールコール、推論コンテンツ（思考連鎖）、マルチリージョンデプロイ
- **対応リージョン**：
  - `beijing` —— 华北2（北京）
  - `virginia` —— 米国（バージニア）
  - `singapore` —— シンガポール
  - `hongkong` —— 中国香港
  - `frankfurt` —— ドイツ（フランクフルト）
- **対応モデル**（API による動的検出、フォールバックリスト付き）：
  - **通義千問シリーズ**：qwen3-max、qwen3.6-plus、qwen3.6-flash、qwen-max、qwen-plus、qwen-turbo、qwen3-coder-plus
  - **推論**：qwq-plus
  - **サードパーティ**：deepseek-v3.2、deepseek-r1、glm-5.1、kimi-k2.5、llama-4-maverick
- **設定**：`apiKey`、`region`、`model`
- **モデル検出**：実行時に百炼 API から利用可能なモデルを取得；ネットワーク障害時はキュレーションリストにフォールバック

### VolcengineArkClient（Volcengine Ark）

- **タイプ**：クラウド AI サービス
- **プロトコル**：OpenAI 互換 API
- **認証**：Bearer トークン（API キー）
- **機能**：ストリーミングおよび非ストリーミングモード対応、内蔵二層レート制御
  - セルフレート制御：リクエスト間の最小間隔を強制
  - サーバーレート制限：429 エラー処理、指数バックオフリトライ
- **設定**：`apiKey`、`endpoint`、`model`
- **特徴**：ByteDance の AI サービス、複数の豆包モデルをサポート

### クライアントファクトリーパターン

各 AI クライアントタイプには、対応する `IAIClientFactory` 実装があります：

- `OllamaClientFactory` —— OllamaClient インスタンスを作成
- `DashScopeClientFactory` —— DashScopeClient インスタンスを作成
- `VolcengineArkClientFactory` —— VolcengineArkClient インスタンスを作成
- `HerdsmanClientFactory` —— HerdsmanClient インスタンスを作成
- `LongCatClientFactory` —— LongCatClient インスタンスを作成
- `QiniuAIClientFactory` —— QiniuAIClient インスタンスを作成

ファクトリーが提供する機能：
- `CreateClient(Dictionary<string, object> config)` —— 設定からクライアントをインスタンス化
- `GetConfigKeyOptions(string key, ...)` —— 設定キーの動的オプション（利用可能なモデル、リージョンなど）を返す
- `GetDisplayName()` —— クライアントタイプのローカライズ表示名

### IAIClient 能力インターフェース

`IAIClient` インターフェースは AI クライアントの能力宣言属性を定義し、`ContextManager` はこれに基づいて適応的に動作を調整します：

| 属性 | 型 | 説明 |
|------|------|------|
| `StreamingMode` | `bool?` | ストリーミングモード対応: true=ストリーミング専用, false=非ストリーミング専用, null=両対応(デフォルト: ストリーミング) |
| `SupportsToolCalls` | `bool?` | ツールコール対応: true=対応, false=非対応(ツール注入を無視), null=不明(デフォルト: 対応) |
| `ContextWindowTokens` | `int?` | コンテキストウィンドウサイズ(トークン数)、固定 MaxContextMessages の代わりにトークン予算カットに使用 |
| `SupportsVision` | `bool?` | ビジョン入力対応: true=画像対応, false=非対応, null=不明(デフォルト: 非対応) |
| `SupportsAudio` | `bool?` | オーディオ入力対応: true=オーディオ対応, false=非対応, null=不明(デフォルト: 非対応) |

## 主要な設計判断

### ストレージをインスタンスクラスとして設計（静的ではなく）

`IStorage` は注入可能なインスタンスとして設計されており、静的ユーティリティではありません。これにより以下が保証されます：

- 直接的なファイルシステムアクセス —— IStorage はシステムの内部永続化チャネルであり、エグゼキューターを経由してルーティング**されません**。
- **AI は IStorage を制御できない** —— エグゼキューターは AI ツール主導の IO を管理し、IStorage はフレームワーク自体の内部データの読み書きを管理します。これらは根本的に異なる関心事です。
- モック実装によるテストが可能。
- 将来的に異なるストレージバックエンドをサポートする際、コンシューマーの変更が不要。

### エグゼキューターをセキュリティ境界として設計

エグゼキューターは I/O 操作の**唯一**の経路です。ディスク、ネットワーク、またはコマンドラインアクセスを必要とするツールは、エグゼキューターを経由**しなければなりません**。この設計により以下が強制されます：

- 各エグゼキューターは**独立したディスパッチスレッド**を持ち、パーミッション検証のためのスレッドロックを備えています。
- 集中パーミッションチェック —— エグゼキューターはビーイングの**プライベートパーミッションマネージャー**に問い合わせます。
- 優先度とタイムアウト制御をサポートするリクエストキュー。
- すべての外部操作の監査ログ。
- 障害隔離 —— あるエグゼキューターの障害が他のエグゼキューターに影響しません。
- サーキットブレーカー —— 連続障害時にエグゼキューターを一時停止し、カスケード障害を防止。

### コンテキストマネージャーを軽量オブジェクトとして設計

毎回の `ExecuteOneRound()` で新しい `ContextManager` インスタンスを作成します：

1. ソウルファイル + 最近のチャット履歴をロード。
2. AI クライアントにリクエストを送信。
3. AI がプレーンテキストを返すまで、ツールコールをループ処理。
4. レスポンスをチャットシステムに永続化。
5. 解放。

これにより、各ラウンドが隔離されステートレスに保たれます。

### クラスオーバーライドによる自己進化

シリコンビーイングは実行時に自身の C# クラスをオーバーライドできます：

1. AI が新しいクラスコードを生成（`SiliconBeingBase` を継承する必要があります）。
2. **コンパイル時参照制御**（主要防御）：コンパイラは許可されたアセンブリリストのみを取得 —— `System.IO`、`System.Reflection` などは除外されるため、危険なコードは型レベルで不可能です。
3. **実行時静的解析**（二次防御）：`SecurityScanner` がコンパイル成功後にコード内の危険なパターンをスキャンします。
4. Roslyn がメモリ内でコードをコンパイル。
5. 成功時：`SiliconBeingManager.ReplaceBeing()` が現在のインスタンスを置き換え、状態を移行し、暗号化コードをディスクに永続化。
6. 失敗時：新しいコードは破棄され、既存の実装が維持。

カスタム `IPermissionCallback` 実装も `ReplacePermissionCallback()` を通じてコンパイルおよび注入でき、ビーイングが独自のパーミッションロジックをカスタマイズできます。

コードはディスク上で AES-256 暗号化されて保存されます。暗号化キーはビーイングの GUID（大文字）から PBKDF2 を通じて派生します。

### WebView ブラウザ自動化システム（新規追加）

システムは **Playwright** ベースの WebView ブラウザ自動化機能を統合しています：

- **個体隔離**：各シリコンビーイングは独立したブラウザインスタンス、Cookie、セッションストレージを持ち、完全に隔離されて互いに干渉しません。
- **ヘッドレスモード**：ブラウザはユーザーに完全に見えないヘッドレスモードで実行され、シリコンビーイングがバックグラウンドで自律的に操作します。
- **WebViewBrowserTool**：完全なブラウザ操作機能を提供：
  - ページナビゲーション、クリック、テキスト入力、ページ内容の取得
  - JavaScript の実行、スクリーンショットの取得、要素の出現待機
  - ブラウザステータス管理とリソースクリーンアップ
- **セキュリティ制御**：すべてのブラウザ操作はパーミッション検証チェーンを通過し、悪意のある Web ページアクセスを防止。

### ナレッジネットワークシステム（新規追加）

システムは**トリプル構造**に基づくナレッジグラフシステムを内蔵しています：

- **知識表現**：「主体-関係-客体」トリプル構造を採用（例：Python-is_a-programming_language）
- **KnowledgeTool**：知識のライフサイクル管理全体を提供：
  - `add`/`query`/`update`/`delete` - 基本 CRUD 操作
  - `search` - フルテキスト検索とキーワードマッチング
  - `get_path` - 2 つの概念間の関連パスを発見
  - `validate` - 知識の完全性チェック
  - `stats` - ナレッジネットワーク統計分析
- **永続化ストレージ**：知識トリプルはファイルシステムに永続化され、時間インデックスクエリをサポート。
- **信頼度スコア**：各知識エントリには信頼度スコア（0-1）があり、知識のファジーマッチングとランキングをサポート。
- **タグ分類**：知識にタグを追加でき、分類と検索に便利。

| `FreeList` | フリーリスト、.spk ファイル内の再利用可能な空間を追跡 |
| `PackFileReader` | パックファイルリーダー、.spk ファイルからデータを読み取り |
| `PackFileWriter` | パックファイルライター、.spk ファイルにデータを書き込み |
| `SpeedyPackAutoCompactor` | 自動圧縮タイマー、定期的に .spk ファイルを圧縮して空き空間を回収 |
| `SpeedyPackRegistry` | プロセスレベルのシングルトンマネージャー、アプリケーション全体で同じ SpeedyPack インスタンスを使用することを保証 |

### ストレージアダプター

SiliconLife.Fast は以下のアダプターを通じて SpeedyPack をシステムインターフェースに統合します：

| アダプター | インターフェース | 説明 |
|--------|------|------|
| `SpeedyStorage` | `IStorage` | 汎用キーバリューストレージアダプター |
| `SpeedyTimeStorage` | `ITimeStorage` | 時間インデックスストレージアダプター |
| `SpeedyWorkNoteStorage` | `IWorkNoteStorage` | ワークノートストレージアダプター |

### 設定オプション

`SpeedyPackOptions` は以下の設定を提供します：

| オプション | 型 | デフォルト値 | 説明 |
|------|------|--------|------|
| `CacheTtl` | `TimeSpan` | 5 分 | キャッシュエントリの生存時間 |
| `MaxCacheEntries` | `int` | 1000 | 最大キャッシュエントリ数 |
| `ReadOnly` | `bool` | false | 読み取り専用モード |

### トランザクションサポート

SpeedyPack は `IPackTransaction` インターフェースを通じてアトミック書き込み操作をサポートします：

- `SpeedyTransaction` がトランザクションメカニズムを実装
- バッチ書き込みの原子性をサポート
- トランザクションコミット時、すべての書き込み操作がすべて成功するか、すべてロールバックされる

## プラグインシステム

SiliconLife はプラグインシステムを通じて機能拡張をサポートし、サードパーティ開発者がプラットフォームに新機能を追加できるようにします。

### コアインターフェース

```csharp
public interface IPlugin
{
    string Id { get; }
    string GetName(Language language);
    string Version { get; }
    string GetDescription(Language language);
    string GetAuthor(Language language);
    void OnLoad();
    void OnStart();
    void OnStop();
    void OnUnload();
}
```

### プラグインローダー

`PluginLoader` は指定されたディレクトリからプラグイン DLL をロードし、厳格なセキュリティチェックを実行します：

1. **ディレクトリスキャン** — プラグインディレクトリ内のすべての .dll ファイルをスキャン
2. **セキュリティスキャン** — プラグインが禁止された名前空間を参照していないかチェック
3. **隔離ロード** — カスタム `AssemblyLoadContext` を使用してプラグインを隔離ロード
4. **ライフサイクル管理** — プラグインの OnLoad、OnStart、OnStop、OnUnload メソッドを呼び出し

### セキュリティサンドボックス

プラグインローダーは以下のセキュリティチェックを実行します：

| チェック項目 | 説明 |
|--------|------|
| 禁止名前空間 | System.IO、System.Net.Http、System.Net.WebSockets、System.Net.Sockets、Microsoft.CodeAnalysis |
| 信頼済みアセンブリホワイトリスト | Google.Protobuf、Newtonsoft.Json、MessagePack、Serilog、Microsoft.Extensions.Logging.Abstractions、Dapper |
| 禁止タイプチェック | プラグイン内で参照されている危険なタイプをスキャン |
| 禁止メンバーチェック | プラグイン内で呼び出されている危険なメソッドをスキャン |

### ツール統合

プラグインは `ITool` インターフェースを実装することでカスタムツールを登録できます：

- `ToolManager.ScanAllPluginAssemblies()` メソッドが、ロード済みのすべてのプラグインから ITool 実装をスキャン
- プラグインツールはツールコールループに自動的に統合
- プラグインツールは同じパーミッションシステムの制約を受けます

### プラグインライフサイクル

```
加载（OnLoad）→ 启动（OnStart）→ 运行中 → 停止（OnStop）→ 卸载（OnUnload）
```

## シリコンビーイングのアクティビティステータス

シリコンビーイングには以下のアクティビティステータスがあります：

| ステータス | 説明 |
|------|------|
| `Idle` | アイドル状態、クロックトリガーを待機 |
| `SingleChat` | 1対1チャット中 |
| `GroupChat` | グループチャット中 |
| `Task` | タスク実行中 |
| `Timer` | タイマー実行中 |
| `Stopped` | 停止済み、連続エラーまたは手動停止による |

**Stopped ステータスメカニズム**：
- シリコンビーイングが連続して 10 回エラーを起こした場合、自動的に `Stopped` ステータスに移行
- Stopped ステータスに入ると、ビーイングはタスクを一切実行しません
- 新しいチャットメッセージが到着すると、エラーカウンターがリセットされ、ビーイングは実行を再開

ステータス遷移：
```
Idle → SingleChat → Idle（チャット完了）
Idle → GroupChat → Idle（グループチャット完了）
Idle → Task → Idle（タスク完了）
Idle → Timer → Idle（タイマー完了）
任意 → Stopped（連続 10 回エラー）
Stopped → Idle（新しいチャットメッセージ到達または手動再起動）
```

## ワークフローエンジン

ワークフローエンジンは、テンプレートベースのステートマシンシステムであり、シリコンビーイングのプロジェクト空間における協調フローを駆動します：

### コアコンポーネント

| コンポーネント | 説明 |
|------|------|
| `WorkflowEngine` | ワークフローエンジンコア、テンプレートとインスタンスを管理、Tick 駆動のステート遷移を実行 |
| `WorkflowTemplate` | ワークフローテンプレート、ステートセットと遷移ルールを定義 |
| `WorkflowInstance` | ワークフローインスタンス、特定のプロジェクトにバインド、現在のステートを追跡 |
| `WorkflowLog` | ワークフローログ、ステート遷移履歴を記録 |

### 動作メカニズム

- **テンプレート登録**：`RegisterTemplate()` を通じてワークフローテンプレートを登録し、ステートと遷移ルールを定義
- **インスタンス作成**：テンプレートからインスタンスを作成し、プロジェクト空間にバインド
- **Tick 駆動**：ステート遷移はメインループの Tick メカニズムによって駆動
- **ログ記録**：すべてのステート遷移が自動的にログに記録

## 記憶フェードメカニズム

`MemoryFadeService` は、生物の記憶の忘却特性をシミュレートする定時減衰サービスです：

### 動作メカニズム

- **定時実行**：`TickObject` を継承し、デフォルトで毎時 1 回の減衰サイクルを実行
- **重要度減衰**：各シリコンビーイングの記憶エントリに減衰アルゴリズムを適用し、重要度スコアを低下
- **自動アーカイブ**：重要度が閾値を下回る記憶を自動的にアーカイブ（`ArchiveFadingMemories()`）
- **統計追跡**：減衰サイクル数、ステータス変更エントリ数などの統計データを記録

### 減衰フロー

```
MemoryFadeService.OnTick()
  └── 遍历所有硅基生命体
       └── being.Memory.ApplyDecay()      # 应用重要性衰减
       └── being.Memory.ArchiveFadingMemories()  # 归档低重要性记忆
```

## プロジェクトワークスペースシステム

プロジェクトワークスペースは、複数のシリコンビーイングの協調をサポートする空間管理メカニズムです：

### コア機能

- **プロジェクトライフサイクル**：作成 → アクティブ → アーカイブ → 破棄
- **ロール割り当て**：シリコンビーイングへのプロジェクトロール割り当てをサポート
- **ツールパーミッション隔離**：プロジェクトレベルのツールパーミッション設定、シリコンビーイングレベルのパーミッションから独立
- **ワークノート**：プロジェクト空間内のページ式ノートシステム、ディレクトリ生成とキーワード検索をサポート
- **タスク追跡**：プロジェクトレベルのタスク管理、作成、割り当て、ステータス追跡をサポート
- **ワークフロー統合**：プロジェクトにワークフローテンプレートをバインドし、協調フローを駆動

### 関連ツール

| ツール | 用途 |
|------|------|
| `ProjectTool` | プロジェクト空間管理（作成、アーカイブ、破棄、ロール割り当て） |
| `ProjectTaskTool` | プロジェクトタスク管理（作成、割り当て、ステータス更新） |
| `ProjectWorkNoteTool` | プロジェクトワークノート（作成、検索、ディレクトリ生成） |
| `ProjectWorkTool` | プロジェクト作業操作（タスク作成、グループチャット、ブロードキャスト、プロジェクト完了） |
